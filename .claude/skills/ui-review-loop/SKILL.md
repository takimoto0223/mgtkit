# UI 作成・レビューの共通ルール (管理者指定・2026-08)

## 進め方

1. UI の注文を受けたら、**実装やモックを作ってそのまま見せない**。
   UI デザイナー役のレビューエージェントと往復し、指摘を反映してから
   **実描画のスクリーンショット付き**で報告する。
2. レビューは**実測主義**: 座標・重なり・コントラスト比・色覚シミュレーション
   などを数字で検証させる。忖度禁止の辛口指定で依頼する。
3. 直す → 再レビューを、下の往復数の範囲で合格まで繰り返す。
   静止画で捉えられない問題 (クリック競合・アニメーション) は
   コード側の検証で補う。

## 厳しさレベル (管理者の言い方で切り替える)

- **「サッと作って」** = 早さ重視。厳しさ 5 段階中 3 で **1 往復**
- **「ちゃんと作って」** = 厳しさ **MAX (5)** で **4〜5 往復**
  (問題が出尽くして合格判定になったら早めに切り上げてよい)
- **指定なし** = 厳しさ 4 で 1〜2 往復を目安に自分で判断

## レビューエージェントのモデル

- 1 巡目 (設計判断を含む本審査) = 質重視モデル (Opus 級以上。Fable 可)
- 2 巡目以降 (実装結果・スクショの検証) = 速いモデル (Sonnet 級)。
  ただし MAX 指定のときは質重視モデルのまま回してよい

## 作る前に公開実装を探す (2026-08 追加)

- 定番がありそうな UI・図 (例: Git グラフ風の履歴図 = gitgraph.js や
  Mermaid gitGraph) は、**ゼロから考える前に公開実装 (OSS) を探して
  参考にする**。呼び方が分からないものは見た目の特徴で検索する
- 目的はトークンと手戻りの節約。そのまま流用できなくても、
  ジオメトリ・配色・操作の慣習を借りてアレンジしてよい
  (ライセンスは確認する。コードを写す場合は互換ライセンスのみ)

## デザインの共通原則

- **アイコン・色・文言は既存のアプリ全体と統一**する。勝手に新しい様式を
  増やさない。ダウンロードは Material の ⬇ (トレイ + 矢印) を使う
- **色は同一トーンのパレットで揃える** (どれか 1 つだけ極端に濃い・
  派手な色を作らない。例: Tailwind の同一段番号でまとめる)
- **情報の重複を作らない**: 図に描いたことをツールチップやリストで
  繰り返さない。図・ホバー・一覧はそれぞれ固有の情報を持たせる
- **対象ユーザーに合わせて専門用語を出さない**
  (構造設計チーム向けでは Git / GitHub 用語は画面に出さない)
- 時系列の図は横軸 = 時間 (左が過去)。存在しない期間 (初回配布より前など)
  は描かない
