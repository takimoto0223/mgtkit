# アプリマネージャー 設計・運用の記録

アプリマネージャー (起動 / 更新 / β版 / 提出 / 承認) の設計判断と運用ルールを
フェーズごとに記録したドキュメント。使い方の概要は README を参照。

## スモークテスト対象ルート

既存アプリ (`app.py`) は全 27 ルート。fixture(実 mgt ファイル)なしで決定的に検証できる範囲を
Level 1 スモークテストとした (`tests/test_smoke_routes.py`):

| 対象 | 期待動作 |
|---|---|
| `GET /` | 200 (index.html 描画、`Cache-Control: no-store`) |
| `GET /api/file`(未許可パス) | 404 + JSON `error` |
| `POST /api/upload`(ファイルなし / ダミーファイル) | 400 / 200 + `path` |
| `POST /api/bundle`(不正 `mode`) | 400 |
| `_check_input_file` ガード付き POST 16 ルート(空 JSON) | 400 + JSON `error` |
| `qr_*` 6 ルート(空 JSON) | **500**(現状動作の固定。`_qr_load` が ValueError を送出するため。400 化は将来の改善候補) |

実出力(PDF/DXF/xlsx)を伴う経路は実 mgt が必要なため、合成テキストによる
パーサ・計算ロジックの回帰テスト (Level 2) でカバーする。

## 承認者の範囲・承認必要数

- 全メンバー承認可(仕様どおり)。提出者本人の自己承認禁止は Phase 5 のマネージャー側で制御。
  public 化後は push 権限を持つ collaborator の承認のみカウントする
  (`reviews.collaborators()`。第三者レビュー対策)。
- 承認必要数は `config.json` の `branch_protection.required_approvals`。
  当初 3 で運用開始し、回転を優先して 2026-08 に **2 へ変更** (現行)。
  変更時は `scripts/setup_repo_protection.sh|bat` を再実行して
  GitHub 側のブランチ保護にも反映する。
- 本リポジトリは 2026-08 に public 化済みで、ブランチ保護は無料で有効。
  (private 個人リポジトリに戻す場合は有料プランが必要になる点に注意。)

## β版のデータ分離

アプリ実装を調査した結果、**DB・設定ファイル・レジストリは一切使用していない**。
アプリが持つ状態は次の 3 つのみ:

1. アップロード一時ファイル: `<TEMP>/mgtkit_uploads/`(`app.py` の `_UPLOAD_DIR`)
2. 生成物: 入力 mgt ファイルと同階層の `mgtkit_out/`(入力の置き場所に従う)
3. 待ち受けポート: `MGTKIT_PORT` 環境変数(既定 8765)

したがって分離方針は:

- 安定版とβ版を**別フォルダに展開**し、β版は `MGTKIT_PORT=8766`(`config.json` の
  `app.port_beta`)で起動する。生成物は入力ファイル位置に従うため衝突しない。
- アップロード一時フォルダのみ両者で共有される。分離するには `MGTKIT_UPLOAD_DIR`
  環境変数対応の小改修が必要 → **Phase 2 で実施**(Phase 1 ではアプリ本体を変更しない)。
- β版バナー表示用の環境変数(例 `MGTKIT_CHANNEL=beta`)も Phase 2 で追加する。

## Phase 2 の決定 (マネージャー: 起動・更新・β版タブ)

- マネージャーは `manager/` パッケージとしてリポジトリに同梱し、
  `python -m manager.main`(または `manager/マネージャー起動.bat`)で起動する。
  UI は Flet (`manager/requirements.txt` で固定)。ロジック(バージョン比較・
  gh ラッパー・展開・起動)は UI 非依存のモジュールに分離し pytest で回帰する。
- インストール配置: `<install_root>/stable/mgtkit/` と
  `<install_root>/beta/<version>/mgtkit/`。**アプリ本体フォルダ名は mgtkit 固定**
  (app.py が親ディレクトリを sys.path に入れて `from mgtkit.x import y` する構造のため)。
  install_root は Windows で `%LOCALAPPDATA%\mgtkit`(config.json の
  `manager.install_root` で変更可)。
- リリース取得は `gh api repos/<repo>/releases` + `gh release download`。
  CI 添付の配布 ZIP(version.json 同梱)を優先し、無い場合(Phase 4 整備前)は
  ソースアーカイブを取得してマネージャーが version.json を補完する。
- アプリ側の小改修(Phase 1 で予告済み):
  - `MGTKIT_UPLOAD_DIR` でアップロード一時フォルダを分離(マネージャーが
    インスタンスごとの `uploads_tmp/` を指定)
  - `MGTKIT_CHANNEL=beta` で画面上部にβ版バナーを表示
- β版フィードバック → PR コメント投稿は仕様どおり Phase 6 で対応(Phase 2 は読み取り系のみ)。

## Phase 3 の決定 (提出タブ)

- 提出フローは UI 非依存の `manager/submit.py` に実装し、
  「準備 (`prepare_submission`) → ユーザー確認 → 確定 (`finalize_submission`)」
  の 2 段階に分割。削除ファイルの意図確認と警告承諾をこの境界で行う。
- 基点特定は ZIP 同梱の version.json の commit SHA のみを使う。
  無い/壊れている/履歴に無い場合は平易な日本語でエラー中断。
- 差分計算は隠し作業クローン (`<install_root>/workrepo`) 上で行い、
  比較は git blob ハッシュ (改行変換の影響なし)。**配布 ZIP に含まれない
  開発用ファイル (tests/ docs/ scripts/ manager/ .github/ 等) は差分対象外**
  とし、提出で削除・変更されない (release.yml の除外リストと同期)。
- 安全チェック: 実行ファイル (.exe .bat .ps1 .sh 等) は即ブロック、
  拡張子ホワイトリスト (config `manager.allowed_extensions`)、
  サイズ/件数上限、簡易秘密情報スキャン (正規表現) は警告→確認の上続行可。
  gitleaks 等の本格スキャンは Phase 4 の CI 側で実施。
- コミットメッセージ (未入力時) と PR 本文は Claude API
  (`manager.claude_model`、既定 claude-opus-5、キーは環境変数
  ANTHROPIC_API_KEY) で自動生成。キー未設定・失敗時は定型文へ
  フォールバックし、提出自体は Claude なしでも完結する。
- 衝突時 (基点より main が先行し同一箇所が変更) の解決フローは
  仕様どおり Phase 5 で実装する。

## Phase 4 の決定 (安全チェック CI・自動修正ループ・β版自動リリース)

- **API キーの運用 (仕様からの変更点)**: 管理者キーを repo Secrets に置いて
  `claude-code-action` を使う方式はやめ、**提出者本人の API キー**を使う。
  - マネージャー初回起動時に「名前 + Claude API キー」の登録を必須化。
    保存先は各自の PC の `<install_root>/settings.json` のみ
    (GitHub には一切送らない。ANTHROPIC_API_KEY 環境変数はフォールバック)。
  - コミットメッセージ/PR 本文生成・自動修正ループはすべて本人キーで実行。
    費用も本人 (所属組織) のキーに紐づく。
- **自動修正ループは Actions ではなくマネージャー側で実行** (`manager/autofix.py`)。
  提出タブの「検証状況」から実行: 失敗ログ取得 (gh run view --log-failed) →
  Claude が原因分析・修正 (structured output) → `[auto-fix]` commit → push →
  再検証待ち。上限 `manager.auto_fix_max_attempts` (既定3) 回。
  上限到達時は平易な3行要約を PR コメントへ投稿。
- **ガード**: tests/ ほか保護領域 (docs/ scripts/ manager/
  .github/) の変更禁止をマネージャー側で二重チェックし、さらに CI 側でも
  `[auto-fix]` コミットに tests/ の diff があれば fail。`[auto-fix]`
  プレフィックスと「原因・対応」のコミットメッセージを必須化。
  禁止パターン (bare except / skip 追加 / アサーション緩和 / 仕様変更) は
  プロンプトに明記。
- **CI (`safety` ジョブ、PR のみ)**: gitleaks による秘密情報スキャン +
  requirements.txt 変更時の pip-audit (検出は warning とし承認時の判断材料に)
  + auto-fix ガード。
- **β版自動リリース (`beta-release` ジョブ)**: `feature/*` からの PR で
  test/safety が green になると、最新安定版 vX.Y の次 (vX.Y+1) に対する
  `-beta.N` を自動採番し、version.json 入り配布 ZIP をプレリリース登録。
  マネージャーのβ版タブに即座に現れる。

## Phase 5 の決定 (承認タブ・衝突解決)

- 承認タブ (`manager/reviews.py` + UI): open PR を承認待ち一覧として表示。
  承認 n/必要数 (黄色マーカー)・承認済みメンバー・却下理由 (平易表示)・
  検証状況・衝突有無を1行に集約。
  - 承認 = `gh pr review --approve`。**自己承認はマネージャー側で禁止**。
  - 却下 = 理由コメント必須 → `--request-changes`。1人でも却下があれば
    リリース不可 (ブロック表示)。
  - 差分表示は「提出者の変更 (紺)」「[auto-fix] による変更 (橙)」の
    色分けファイル一覧 + unified diff。判定はコミットメッセージの
    [auto-fix] プレフィックス。
  - リリースボタンは「必要数承認・却下なし・検証OK・衝突なし」で有効。
    既定では**必要数の承認がそろえば誰でもリリース可** (承認プロセス自体が
    品質ゲートのため)。特定メンバーに限定したい場合のみ config
    `manager.admins` に名前を並べる。
    実行内容 = squash merge → 次の正式版 vX.Y を採番 →
    release ワークフローを dispatch (リリースノートは Claude 生成、
    フォールバックあり)。
- 差し戻し後の再提出: 提出ダイアログに「既存の提出 #N に修正版として積む」
  の選択肢を追加 (同一 PR にコミットが積まれる)。
- 衝突解決 (`manager/conflicts.py`): merge 試行で衝突検出 → Claude が
  「機能レベルの説明」に翻訳 → 3択 (両方残す[推奨]/自分優先/最新版優先)。
  自分優先・最新版優先は git で機械的に解決し、**「両方残す」のみ Claude が
  コードレベル統合** (統合結果は衝突ファイル以外への変更・マーカー残りを
  検査して適用)。統合ボタンは提出者本人にのみ表示。
- セキュリティ強化: settings.json (個人設定) を提出対象から常に除外、
  API キー・トークン・秘密鍵の検出を「警告」から「即ブロック」へ格上げ。

## Phase 6 の決定 (通知・フィードバック・セットアップ)

- 更新通知: マネージャー起動時 + 30分ごとのポーリングで GitHub Releases を
  確認し、新しい安定版があれば起動タブに通知バナーを表示する。
- β版フィードバック (`manager/feedback.py`): β版タブの各リリースに
  フィードバック入力を用意し、リリースノート中の「提出 #N」から対応 PR を
  特定して `gh pr comment` で投稿。登録済みの名前を添えて承認判断の材料に
  する。対応 PR が特定できないリリース (手動作成等) は送信不可。
- `scripts/setup.bat` (メンバー配布用): winget で Git / gh / Python を導入
  → `gh auth login` (ブラウザ認証) → `%USERPROFILE%\mgtkit` へ clone →
  マネージャー起動まで。このファイル 1 つを渡すだけで新メンバーの環境が整う。
- README にアプリマネージャーの節と構成表の更新を追加。

## 運用改善の決定 (2026-08, 提出 #27〜#50)

実運用を始めて出た要望への対応。**判断の理由**も残す (後から読む人のため)。

### 提出まわり

- **対象外ファイルはエラーにせず除外** (`submit.filter_unsupported`):
  .pdf・.bat 等が ZIP に混ざっても提出を止めず、差分からだけ外す。
  理由 =「フォルダ丸ごと ZIP で OK」の体験をファイル種類の面でも守るため。
  ブロック (即エラー) は秘密情報の混入のみ。
- **ファイルごとの変更説明**: 提出時に 1 回だけ Claude が生成し PR 本文の
  「## 変更ファイルの説明」節に保存 (`- パス — 説明` 形式)。差分ビューワが
  これを読んで表示する。理由 = 表示のたびに生成するとキー・費用・待ち時間が
  レビュー側に発生するため「書いた本人のキーで 1 回だけ」。機械的な
  関数名抽出は不採用 (意図が伝わらないため)。再提出時は本文を作り直す。
- **usage.json / settings.json / version.json は提出対象から常に除外**
  (GENERATED_FILES)。個人情報・生成物がリポジトリに乗らないように。

### 承認・却下・衝突

- **承認タブは feature/ ブランチの PR のみ表示** (SUBMISSION_BRANCH_PREFIX)。
  マネージャー自体の開発 PR (claude/* 等) はメンバーの承認対象ではないため。
- **承認/却下はトグル**: 2 回目のクリックで自分のレビューを取り消して
  ニュートラルに戻せる (`reviews.cancel_my_review`)。
- **却下確定 (必要数の却下)**: カードをグレーアウトし、3 日後に日次の
  GitHub Actions (`reject-cleanup.yml`) が PR クローズ + β版削除。
  残り日数カウンター表示。各自「非表示」で一覧の最下部に畳める
  (PC ローカルの `local_state.json`。他人には影響しない)。
- **提出者の「取り下げ」**: 提出者本人にだけ表示。PR クローズ +
  ブランチ削除 + 対応β版の削除まで自動で行う。
- **衝突時は「統合待ちロック」**: 衝突した提出はカード全体を薄くし、
  提出者の「最新版と統合 / 取り下げ」以外の操作を無効化。統合後は
  **全員の承認・却下をリセット** (`reviews.reset_all_reviews`) し、
  フィードバック件数も新しいβ版宛てで数え直す。
  理由 = 統合で中身が変わった提出を古い承認のまま通さないため。
- **リリースされた提出のβ版は自動削除** (`reviews.delete_betas_for`)。
  β版タブには「いま確認してほしいもの」だけが残る。
- **必要数の承認がそろった瞬間に自動リリース** (2026-08):
  2 人目の承認者の端末でそのままリリースが実行される。承認を
  「最後のひと押し」にしてレビューのレスポンスを促すため。
  検証NG・却下あり・衝突中・権限なしのときは発射せず、従来どおり
  リリースボタン待ち (ボタンはフォールバックとして残置)。
- **ロケット演出** (飾り・操作不可): 承認 1 つ = 点火 🔥 (タブを
  開いたとき一度だけ)、自動リリース = 点火 → 機体が震える → 加速離陸
  (発射地点に煙) → 機体を傾けて更新タブへ → ✨ と弾けて消える、
  却下 1 つ = 煙 💨、却下確定 = ぐらつき → 転倒 → 爆発 💥 → 煙。
  承認・却下の反応を促すためのゲーミフィケーション。演出は全て
  3 秒以内・絵文字数個だけで作り、動作は軽く保つ (凝った見た目と
  軽さの両立が狙い)。
- **ロケット演出のベクター化 (`manager/rocketfx.py`)** (2026-08):
  絵文字 2 個の平行移動では「動きの説得力ゼロ」で、承認を促す肝の
  演出として機能しないため、機体・炎・煙・破片を自前の SVG 絵にして
  約 30fps のフレームアニメーションに全面刷新。
  - Flet の Image は SVG 文字列をそのまま描画できる (ただし SVG の
    filter は効かないため、光のにじみはグラデーションで表現)
  - 基点は**カード右の常駐ロケット位置**に固定。発射も転倒・爆発も
    そこから始まる (画面中央に突然現れると意味不明なため)
  - 爆発は火の玉を機体に重ね、同時に機体が 7 パーツ (ノーズ・窓・
    胴体上下・フィン×2・ノズル) に分解して放物線で飛散、カード上に
    散乱する。畳んだ行の行頭には残骸の静止画が残る
  - 演出中だけ背景スレッドが動き、終了時に overlay を片づける。
    普段の画面には影響しない
- **リリースボタンの廃止** (2026-08): 自動リリースがあるため手動の
  リリースボタンは削除し、その位置 (ボタン列の末尾) に常駐ロケットを
  移した。承認がそろったまま未リリースの提出 (機能導入前に承認済み
  だったもの・2 人目の承認時にリリースが失敗したもの) が詰まないよう、
  権限のある人がタブを開いたときに条件を満たす提出を自動でリリース
  する (発射演出つき。失敗した提出はそのセッション中は再試行しない)。
- **リリース前にブランチを自動で最新化する** (2026-08): ブランチ保護
  が「最新の状態でのみマージ可」(strict_status_checks) のため、main
  より古い提出はそのままでは正式版に取り込めず、自動リリースが
  黙って失敗していた (承認 2/2 の #31 で発覚)。リリース時に古ければ
  取り込み直し (update-branch) → 検証の完了を待つ (最大約 8 分) →
  マージ、の順に自動化。時間のかかる工程は発射演出の**前**に済ませ、
  ✨ のあとに確実にカードが消えるようにする。取り込み直しで検証が
  走り直すため新しいβ版がもう 1 つ発行されることがあるが、リリース
  時の掃除で提出に紐づくβ版は削除されるので実害はない。
- **更新バッジは 3 状態** (2026-08): リリース直後は公開処理 (数分) が
  終わっておらず「更新なし」と判定されるため、楽観的に黄色を点けると
  直後の定期チェックが消してしまい、更新タブに行っても「最新です」と
  出て信頼を失う。✨直後はグレーの「…」(準備中)、公開を確認できたら
  黄色の件数、10 分待っても確認できなければ案内文つきで消灯、の
  3 段階にした (UI レビューの提案)。公開待ちの間は定期チェックが
  バッジを消さない。定期チェック自体も 30 分→10 分に短縮 (他メンバー
  の気づき遅れ対策)。
- **常駐ロケットはボタン行の右端に右寄せ** (2026-08): ボタン列に
  直接並べると発射・爆発の基点 x がボタン構成 (試すボタンの有無や
  文言の長さ) で変わり座標がずれるため、spacer で右寄せにして
  ウィンドウ幅から x を確定させた。操作ボタンと「状態の絵」の分離
  にもなる。y は一覧描画時にカードごとの行数から推定して記録し、
  2 枚目以降のカードでも自分の位置から発射・転倒する。全状態を
  高さ 36px の固定舞台に載せ、機体と地面の位置がぶれないようにした。
  状態の意味はツールチップで補足 (装飾を「読める部品」にする)。
- **却下取り消し時にローカル記録も掃除** (2026-08): 却下確定→取り消し
  →再確定の 2 周目でも自動で畳めるよう、取り消し成功時に非表示・
  自動畳みの記録 (hidden_prs / auto_folded) を消す。
- **カードの削除・畳みは演出が終わってから** (2026-08): 発射なら
  ✨ が光った直後にカードが一覧から消え、同時に「更新」タブの
  バッジが自動で立つ。爆発なら破片が落ちきってから非表示エリアへ
  畳む。演出の途中でカードが消えると「何が起きたか」が伝わらない
  ため。演出中は該当カードの常駐ロケットを隠し、overlay の機体との
  二重表示を防ぐ。一覧に戻した却下確定カードにはロケットを出さない
  (却下が期日内に取り消されれば状態が変わり、煙付きで再表示される)。
- **却下確定した提出は自動で一覧下の「非表示」へ畳む** (2026-08):
  爆発演出のあと勝手に消えたように見えないよう、下の非表示欄に
  移動して「一覧に戻す」で戻せる。自動で畳んだ記録は
  `local_state.json` の `auto_folded` に残し、本人が「一覧に戻す」を
  押した提出を次回起動時に再び畳み直さないようにする。

### 差分ビューワ (`manager/diffview.py`)

- 「差分」クリックで**既定ブラウザに自己完結 HTML を直接開く** (依存なし・
  難しい画面遷移なし)。フォルダ比較 + 左右並びファイル比較、変更のない行は
  折りたたみ、パスは手元の見え方に合わせ `mgtkit/` 前置。
- **確認用データのダウンロード**は差分ビューワの右上にのみ置く
  (β版タブに置くと誤って使う人が出るため)。クリック時に資料
  「バージョン管理と同時開発のしくみ」4.2 の 3 リスクをイラスト付き
  モーダルで確認してから DL。ZIP (`#N_確認用.zip`) は
  「一式/」(動作チェック用) + 「変更のみ/」(中身チェック用) + 説明 txt。
  **一式に version.json を意図的に入れない** = そのフォルダを ZIP にしても
  マネージャーから提出できず、誤って開発の土台にできない仕組み。
- **確認用 ZIP の「一式」は「最新の正式版 + この提出の変更」の重ね合わせ**
  で作る (= 実際のβ版と同じ中身)。提出ブランチの木をそのまま使うと、
  基点時点に存在してその後 main 側で削除・移動されたファイルが
  紛れ込むため (app-manager-spec.md 混入の不具合の原因)。
- **DL ボタンの文言は「β版データ (確認用) をダウンロード」**:
  当初の「更新データ」は更新タブの正式な更新と紛らわしいため、
  中身 (β版) と用途 (確認) が伝わる名称に変更。
- **差分の配色は意味と 1 対 1**: 赤 = 変更前 (変更行の左)、
  緑 = 変更後・追加、紺 (薄い紺 + 取り消し線) = 削除された行。
  当初は変更行の左と削除行が同じ赤で「赤 = 削除」の凡例が不正確だった。
  凡例は「赤・緑・紺」の漢字一字で統一。
- **ファイルごとの変更説明はファイル名と同じ行の右横**に表示
  (フォルダ比較・ファイル比較とも)。段を分けると一覧が縦に伸びるため。

### その他

- **git は常に `core.quotepath=off` で実行** (`gitcli.run_git`):
  既定では日本語ファイル名がエスケープ表記 (`"\346..."`) で出力され、
  パスの照合に失敗して差分表示や確認用 ZIP から日本語名ファイルが
  静かに欠落するため。
- **CLAUDE.md / .gitattributes は配布・提出対象外** (DIST_EXCLUDE_FILES
  と release.yml / test.yml の zip 除外に追加)。開発用ファイルの除外は
  3 箇所 (submit.py・release.yml・test.yml) の同期が必要。
- **参加申請 Issue にオーナー @メンション**を必ず入れる
  (メンションがないと GitHub の通知メールが飛ばないため)。
- **マネージャー起動.bat は起動前に `git pull --ff-only`**: 常に最新の
  マネージャーで起動される (メンバーに Git 操作を意識させない)。
- **mgtkit フォルダの直接変更は起動時に自動で退避して最新化**
  (`manager/selfupdate.py`): 直接編集があると pull が止まり、本人が
  気づかないまま全体が古いままになる事故 (実際に発生) の再発防止。
  黙って破棄はせず、見える退避フォルダ `<mgtkit>/stash/日時/` に
  実ファイルと差分ビューワ HTML を保存してから破棄・更新し、UI が

  触れず、ローカルコミットがある場合 (管理者の開発クローン) は
  何もしない。stash/ は .gitignore と JUNK_DIRS で提出対象外。
- **API 利用量・料金グラフ** (`manager/usage.py` + ヘッダー右上の棒グラフ):
  API 応答のたびに `<install_root>/usage.json` へ日別積算。
  金額は**記録時点の単価で確定保存** (後から config の単価を変えても
  過去の記録は変わらない)。単価・円レートは config
  `manager.api_pricing` / `usd_jpy_rate`。表示はこの PC のマネージャー
  経由分のみの「目安」で、正確な請求は Claude Console。

## 更新が「展開中...」のまま失敗する不具合の修正 (2026-08)

アプリ (本体の画面) を開いたまま「更新して起動」を押すと、更新が
「展開中...」のまま進まなくなる不具合があった。原因と対策:

- **原因**: 本体のサーバーはアプリのフォルダ (`stable/mgtkit/`) の中で
  動いているため、Windows ではそのフォルダが「使用中」になり削除できない。
  さらに従来の置き換え方式 (先に全部消してからコピー) は、失敗すると
  **途中まで消えた壊れた状態**が残った。サーバーはマネージャーを閉じても
  動き続けるので、マネージャーを入れ直しても毎回同じ失敗になる。
  エラーは画面の小さい文字にしか出ず、ログには何も残らなかったため
  「止まったまま」に見えた。
- **更新の前に起動中のアプリを自動で終了する** (`launcher.stop_app`)。
  ポートの使用プロセスを調べて終了させる方式にした。マネージャーが起動
  プロセスを覚えておく案は、マネージャーを再起動すると前回起動した
  サーバーを止められなくなるため選ばなかった。誤終了を避けるため、
  ポートを python 以外のプログラムが使っている場合は終了させない。
  なお終了はどのみち必要 (起動したままだと更新後もポートが使用中で、
  「更新して起動」が古い画面を開き直すだけになる)。
- **フォルダの置き換えは「新しい内容を先に用意 → 名前の付け替え」方式**
  (`installer._replace_dir`)。付け替えに失敗しても元のインストールが
  無傷で残り、平易なメッセージのエラーになる。
- **更新・起動まわりの失敗はログにも記録する** (`log.exception`)。
  画面の文字だけだと今回のように原因調査ができないため。

## フォルダ構成の整理 (2026-08)

「mgtkit」は本体 + アプリマネージャー + 資料の**総称**、構造設計プログラム
としての本体はルート直下、という整理に基づき、**アプリマネージャー関係の
ファイルを `manager/` に完結**させた。

- 移動したもの: 開発メモ (CLAUDE.md → manager/CLAUDE.md)、設計記録
  (docs/ → manager/docs/decisions.md)、セットアップスクリプト
  (scripts/ → manager/scripts/)、マネージャーの資料 PDF
  (readme/ → manager/readme/)、マネージャーのテスト
  (tests/test_manager_* → manager/tests/)。README も本体用とマネージャー用に分割
- **本体プログラムのパスは動かさない**: 提出の差分は「基点コミット vs ZIP」の
  比較で対象は配布対象ファイルのみのため、対象外のファイル移動なら
  作業中のメンバーの提出に影響しない (本体を動かすと全ファイル移動扱いに
  なり移行の谷が生じる — 見送りの理由)
- ルートに残す例外: `.github/` (GitHub の仕様で固定)、`config.json`
  (本体ポートも含む共通運用設定)、`pytest.ini` / `requirements-dev.txt` (開発共通)
- 資料 PDF は クローン (mgtkit フォルダ) の起動時自動更新で配られる。
  配布 ZIP (実行用コピー) には本体の操作マニュアルのみ入る

## リリース手順 (Phase 4 自動化までの暫定運用)

- `.github/workflows/release.yml`(手動実行)で安定版/β版を Releases に登録する。
  GitHub の Actions タブ → release → Run workflow でバージョン(vX.Y または
  vX.Y-beta.N)とリリースノートを入力する。
- version.json の生成と配布 ZIP(開発用ファイル除外)の添付はワークフローが行う。
  vX.Y-beta.N はプレリリースフラグ付きで登録される。
- Phase 4 で「PR マージ → 自動タグ付け・自動リリース」に置き換える際も
  この ZIP 作成手順を流用する。
