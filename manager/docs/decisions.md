# アプリマネージャー 設計・運用の記録

アプリマネージャー (起動 / 更新 / β版 / 提出 / 承認) の設計判断と運用ルールを
フェーズごとに記録したドキュメント。使い方の概要は README を参照。

## スモークテスト対象ルート

既存アプリ (`app.py`) は全 27 ルート。fixture(実 mgt ファイル)なしで決定的に検証できる範囲を
Level 1 スモークテストとした (`tests/test_smoke_routes.py`):

| 対象 | 期待動作 |
|---|---|
| `GET /` | 200 (index.html 描画、`Cache-Control: no-store`) |
| `GET /api/file`(未許可パス) | 404 + JSON `error` |
| `POST /api/upload`(ファイルなし / ダミーファイル) | 400 / 200 + `path` |
| `POST /api/bundle`(不正 `mode`) | 400 |
| `_check_input_file` ガード付き POST 16 ルート(空 JSON) | 400 + JSON `error` |
| `qr_*` 6 ルート(空 JSON) | **500**(現状動作の固定。`_qr_load` が ValueError を送出するため。400 化は将来の改善候補) |

実出力(PDF/DXF/xlsx)を伴う経路は実 mgt が必要なため、合成テキストによる
パーサ・計算ロジックの回帰テスト (Level 2) でカバーする。

## 承認者の範囲・承認必要数

- 全メンバー承認可(仕様どおり)。提出者本人の自己承認禁止は Phase 5 のマネージャー側で制御。
  public 化後は push 権限を持つ collaborator の承認のみカウントする
  (`reviews.collaborators()`。第三者レビュー対策)。
- 承認必要数は `config.json` の `branch_protection.required_approvals`。
  当初 3 で運用開始し、回転を優先して 2026-08 に **2 へ変更** (現行)。
  変更時は `scripts/setup_repo_protection.sh|bat` を再実行して
  GitHub 側のブランチ保護にも反映する。
- 本リポジトリは 2026-08 に public 化済みで、ブランチ保護は無料で有効。
  (private 個人リポジトリに戻す場合は有料プランが必要になる点に注意。)

## β版のデータ分離

アプリ実装を調査した結果、**DB・設定ファイル・レジストリは一切使用していない**。
アプリが持つ状態は次の 3 つのみ:

1. アップロード一時ファイル: `<TEMP>/mgtkit_uploads/`(`app.py` の `_UPLOAD_DIR`)
2. 生成物: 入力 mgt ファイルと同階層の `mgtkit_out/`(入力の置き場所に従う)
3. 待ち受けポート: `MGTKIT_PORT` 環境変数(既定 8765)

したがって分離方針は:

- 安定版とβ版を**別フォルダに展開**し、β版は `MGTKIT_PORT=8766`(`config.json` の
  `app.port_beta`)で起動する。生成物は入力ファイル位置に従うため衝突しない。
- アップロード一時フォルダのみ両者で共有される。分離するには `MGTKIT_UPLOAD_DIR`
  環境変数対応の小改修が必要 → **Phase 2 で実施**(Phase 1 ではアプリ本体を変更しない)。
- β版バナー表示用の環境変数(例 `MGTKIT_CHANNEL=beta`)も Phase 2 で追加する。

## Phase 2 の決定 (マネージャー: 起動・更新・β版タブ)

- マネージャーは `manager/` パッケージとしてリポジトリに同梱し、
  `python -m manager.main`(または `manager/マネージャー起動.bat`)で起動する。
  UI は Flet (`manager/requirements.txt` で固定)。ロジック(バージョン比較・
  gh ラッパー・展開・起動)は UI 非依存のモジュールに分離し pytest で回帰する。
- インストール配置: `<install_root>/stable/mgtkit/` と
  `<install_root>/beta/<version>/mgtkit/`。**アプリ本体フォルダ名は mgtkit 固定**
  (app.py が親ディレクトリを sys.path に入れて `from mgtkit.x import y` する構造のため)。
  install_root は Windows で `%LOCALAPPDATA%\mgtkit`(config.json の
  `manager.install_root` で変更可)。
- リリース取得は `gh api repos/<repo>/releases` + `gh release download`。
  CI 添付の配布 ZIP(version.json 同梱)を優先し、無い場合(Phase 4 整備前)は
  ソースアーカイブを取得してマネージャーが version.json を補完する。
- アプリ側の小改修(Phase 1 で予告済み):
  - `MGTKIT_UPLOAD_DIR` でアップロード一時フォルダを分離(マネージャーが
    インスタンスごとの `uploads_tmp/` を指定)
  - `MGTKIT_CHANNEL=beta` で画面上部にβ版バナーを表示
- β版フィードバック → PR コメント投稿は仕様どおり Phase 6 で対応(Phase 2 は読み取り系のみ)。

## Phase 3 の決定 (提出タブ)

- 提出フローは UI 非依存の `manager/submit.py` に実装し、
  「準備 (`prepare_submission`) → ユーザー確認 → 確定 (`finalize_submission`)」
  の 2 段階に分割。削除ファイルの意図確認と警告承諾をこの境界で行う。
- 基点特定は ZIP 同梱の version.json の commit SHA のみを使う。
  無い/壊れている/履歴に無い場合は平易な日本語でエラー中断。
- 差分計算は隠し作業クローン (`<install_root>/workrepo`) 上で行い、
  比較は git blob ハッシュ (改行変換の影響なし)。**配布 ZIP に含まれない
  開発用ファイル (tests/ docs/ scripts/ manager/ .github/ 等) は差分対象外**
  とし、提出で削除・変更されない (release.yml の除外リストと同期)。
- 安全チェック: 実行ファイル (.exe .bat .ps1 .sh 等) は即ブロック、
  拡張子ホワイトリスト (config `manager.allowed_extensions`)、
  サイズ/件数上限、簡易秘密情報スキャン (正規表現) は警告→確認の上続行可。
  gitleaks 等の本格スキャンは Phase 4 の CI 側で実施。
- コミットメッセージ (未入力時) と PR 本文は Claude API
  (`manager.claude_model`、既定 claude-opus-5、キーは環境変数
  ANTHROPIC_API_KEY) で自動生成。キー未設定・失敗時は定型文へ
  フォールバックし、提出自体は Claude なしでも完結する。
- 衝突時 (基点より main が先行し同一箇所が変更) の解決フローは
  仕様どおり Phase 5 で実装する。

## Phase 4 の決定 (安全チェック CI・自動修正ループ・β版自動リリース)

- **API キーの運用 (仕様からの変更点)**: 管理者キーを repo Secrets に置いて
  `claude-code-action` を使う方式はやめ、**提出者本人の API キー**を使う。
  - マネージャー初回起動時に「名前 + Claude API キー」の登録を必須化。
    保存先は各自の PC の `<install_root>/settings.json` のみ
    (GitHub には一切送らない。ANTHROPIC_API_KEY 環境変数はフォールバック)。
  - コミットメッセージ/PR 本文生成・自動修正ループはすべて本人キーで実行。
    費用も本人 (所属組織) のキーに紐づく。
- **自動修正ループは Actions ではなくマネージャー側で実行** (`manager/autofix.py`)。
  提出タブの「検証状況」から実行: 失敗ログ取得 (gh run view --log-failed) →
  Claude が原因分析・修正 (structured output) → `[auto-fix]` commit → push →
  再検証待ち。上限 `manager.auto_fix_max_attempts` (既定3) 回。
  上限到達時は平易な3行要約を PR コメントへ投稿。
- **ガード**: tests/ ほか保護領域 (docs/ scripts/ manager/
  .github/) の変更禁止をマネージャー側で二重チェックし、さらに CI 側でも
  `[auto-fix]` コミットに tests/ の diff があれば fail。`[auto-fix]`
  プレフィックスと「原因・対応」のコミットメッセージを必須化。
  禁止パターン (bare except / skip 追加 / アサーション緩和 / 仕様変更) は
  プロンプトに明記。
- **CI (`safety` ジョブ、PR のみ)**: gitleaks による秘密情報スキャン +
  requirements.txt 変更時の pip-audit (検出は warning とし承認時の判断材料に)
  + auto-fix ガード。
- **β版自動リリース (`beta-release` ジョブ)**: `feature/*` からの PR で
  test/safety が green になると、最新安定版 vX.Y の次 (vX.Y+1) に対する
  `-beta.N` を自動採番し、version.json 入り配布 ZIP をプレリリース登録。
  マネージャーのβ版タブに即座に現れる。

## Phase 5 の決定 (承認タブ・衝突解決)

- 承認タブ (`manager/reviews.py` + UI): open PR を承認待ち一覧として表示。
  承認 n/必要数 (黄色マーカー)・承認済みメンバー・却下理由 (平易表示)・
  検証状況・衝突有無を1行に集約。
  - 承認 = `gh pr review --approve`。**自己承認はマネージャー側で禁止**。
  - 却下 = 理由コメント必須 → `--request-changes`。1人でも却下があれば
    リリース不可 (ブロック表示)。
  - 差分表示は「提出者の変更 (紺)」「[auto-fix] による変更 (橙)」の
    色分けファイル一覧 + unified diff。判定はコミットメッセージの
    [auto-fix] プレフィックス。
  - リリースボタンは「必要数承認・却下なし・検証OK・衝突なし」で有効。
    既定では**必要数の承認がそろえば誰でもリリース可** (承認プロセス自体が
    品質ゲートのため)。特定メンバーに限定したい場合のみ config
    `manager.admins` に名前を並べる。
    実行内容 = squash merge → 次の正式版 vX.Y を採番 →
    release ワークフローを dispatch (リリースノートは Claude 生成、
    フォールバックあり)。
- 差し戻し後の再提出: 提出ダイアログに「既存の提出 #N に修正版として積む」
  の選択肢を追加 (同一 PR にコミットが積まれる)。
- 衝突解決 (`manager/conflicts.py`): merge 試行で衝突検出 → Claude が
  「機能レベルの説明」に翻訳 → 3択 (両方残す[推奨]/自分優先/最新版優先)。
  自分優先・最新版優先は git で機械的に解決し、**「両方残す」のみ Claude が
  コードレベル統合** (統合結果は衝突ファイル以外への変更・マーカー残りを
  検査して適用)。統合ボタンは提出者本人にのみ表示。
- セキュリティ強化: settings.json (個人設定) を提出対象から常に除外、
  API キー・トークン・秘密鍵の検出を「警告」から「即ブロック」へ格上げ。

## Phase 6 の決定 (通知・フィードバック・セットアップ)

- 更新通知: マネージャー起動時 + 30分ごとのポーリングで GitHub Releases を
  確認し、新しい安定版があれば起動タブに通知バナーを表示する。
- β版フィードバック (`manager/feedback.py`): β版タブの各リリースに
  フィードバック入力を用意し、リリースノート中の「提出 #N」から対応 PR を
  特定して `gh pr comment` で投稿。登録済みの名前を添えて承認判断の材料に
  する。対応 PR が特定できないリリース (手動作成等) は送信不可。
- `scripts/setup.bat` (メンバー配布用): winget で Git / gh / Python を導入
  → `gh auth login` (ブラウザ認証) → `%USERPROFILE%\mgtkit` へ clone →
  マネージャー起動まで。このファイル 1 つを渡すだけで新メンバーの環境が整う。
- README にアプリマネージャーの節と構成表の更新を追加。

## 運用改善の決定 (2026-08, 提出 #27〜#50)

実運用を始めて出た要望への対応。**判断の理由**も残す (後から読む人のため)。

### 提出まわり

- **対象外ファイルはエラーにせず除外** (`submit.filter_unsupported`):
  .pdf・.bat 等が ZIP に混ざっても提出を止めず、差分からだけ外す。
  理由 =「フォルダ丸ごと ZIP で OK」の体験をファイル種類の面でも守るため。
  ブロック (即エラー) は秘密情報の混入のみ。
- **ファイルごとの変更説明**: 提出時に 1 回だけ Claude が生成し PR 本文の
  「## 変更ファイルの説明」節に保存 (`- パス — 説明` 形式)。差分ビューワが
  これを読んで表示する。理由 = 表示のたびに生成するとキー・費用・待ち時間が
  レビュー側に発生するため「書いた本人のキーで 1 回だけ」。機械的な
  関数名抽出は不採用 (意図が伝わらないため)。再提出時は本文を作り直す。
- **usage.json / settings.json / version.json は提出対象から常に除外**
  (GENERATED_FILES)。個人情報・生成物がリポジトリに乗らないように。

### 承認・却下・衝突

- **承認タブは feature/ ブランチの PR のみ表示** (SUBMISSION_BRANCH_PREFIX)。
  マネージャー自体の開発 PR (claude/* 等) はメンバーの承認対象ではないため。
- **承認/却下はトグル**: 2 回目のクリックで自分のレビューを取り消して
  ニュートラルに戻せる (`reviews.cancel_my_review`)。
- **却下確定 (必要数の却下)**: カードをグレーアウトし、3 日後に日次の
  GitHub Actions (`reject-cleanup.yml`) が PR クローズ + β版削除。
  残り日数カウンター表示。各自「非表示」で一覧の最下部に畳める
  (PC ローカルの `local_state.json`。他人には影響しない)。
- **提出者の「取り下げ」**: 提出者本人にだけ表示。PR クローズ +
  ブランチ削除 + 対応β版の削除まで自動で行う。
- **衝突時は「統合待ちロック」**: 衝突した提出はカード全体を薄くし、
  提出者の「最新版と統合 / 取り下げ」以外の操作を無効化。統合後は
  **全員の承認・却下をリセット** (`reviews.reset_all_reviews`) し、
  フィードバック件数も新しいβ版宛てで数え直す。
  理由 = 統合で中身が変わった提出を古い承認のまま通さないため。
- **リリースされた提出のβ版は自動削除** (`reviews.delete_betas_for`)。
  β版タブには「いま確認してほしいもの」だけが残る。
- **必要数の承認がそろった瞬間に自動リリース** (2026-08):
  2 人目の承認者の端末でそのままリリースが実行される。承認を
  「最後のひと押し」にしてレビューのレスポンスを促すため。
  検証NG・却下あり・衝突中・権限なしのときは発射せず、従来どおり
  リリースボタン待ち (ボタンはフォールバックとして残置)。
- **ロケット演出** (飾り・操作不可): 承認 1 つ = 点火 🔥 (タブを
  開いたとき一度だけ)、自動リリース = 点火 → 機体が震える → 加速離陸
  (発射地点に煙) → 機体を傾けて更新タブへ → ✨ と弾けて消える、
  却下 1 つ = 煙 💨、却下確定 = ぐらつき → 転倒 → 爆発 💥 → 煙。
  承認・却下の反応を促すためのゲーミフィケーション。演出は全て
  3 秒以内・絵文字数個だけで作り、動作は軽く保つ (凝った見た目と
  軽さの両立が狙い)。
- **ロケット演出のベクター化 (`manager/rocketfx.py`)** (2026-08):
  絵文字 2 個の平行移動では「動きの説得力ゼロ」で、承認を促す肝の
  演出として機能しないため、機体・炎・煙・破片を自前の SVG 絵にして
  約 30fps のフレームアニメーションに全面刷新。
  - Flet の Image は SVG 文字列をそのまま描画できる (ただし SVG の
    filter は効かないため、光のにじみはグラデーションで表現)
  - 基点は**カード右の常駐ロケット位置**に固定。発射も転倒・爆発も
    そこから始まる (画面中央に突然現れると意味不明なため)
  - 爆発は火の玉を機体に重ね、同時に機体が 7 パーツ (ノーズ・窓・
    胴体上下・フィン×2・ノズル) に分解して放物線で飛散、カード上に
    散乱する。畳んだ行の行頭には残骸の静止画が残る
  - 演出中だけ背景スレッドが動き、終了時に overlay を片づける。
    普段の画面には影響しない
- **リリースボタンの廃止** (2026-08): 自動リリースがあるため手動の
  リリースボタンは削除し、その位置 (ボタン列の末尾) に常駐ロケットを
  移した。承認がそろったまま未リリースの提出 (機能導入前に承認済み
  だったもの・2 人目の承認時にリリースが失敗したもの) が詰まないよう、
  権限のある人がタブを開いたときに条件を満たす提出を自動でリリース
  する (発射演出つき。失敗した提出はそのセッション中は再試行しない)。
- **リリース前にブランチを自動で最新化する** (2026-08): ブランチ保護
  が「最新の状態でのみマージ可」(strict_status_checks) のため、main
  より古い提出はそのままでは正式版に取り込めず、自動リリースが
  黙って失敗していた (承認 2/2 の #31 で発覚)。リリース時に古ければ
  取り込み直し (update-branch) → 検証の完了を待つ (最大約 8 分) →
  マージ、の順に自動化。時間のかかる工程は発射演出の**前**に済ませ、
  ✨ のあとに確実にカードが消えるようにする。取り込み直しで検証が
  走り直すため新しいβ版がもう 1 つ発行されることがあるが、リリース
  時の掃除で提出に紐づくβ版は削除されるので実害はない。
- **公開待ちが長引いたときは処理中と失敗を見分けて案内** (2026-08):
  10 分待っても公開が確認できないとき、以前は一律に「公開されると
  自動で取り込みます」と案内していたが、リリース処理が失敗している
  場合は待っても永久に来ない。`reviews.release_run_status` で最後の
  実行結果を見て、失敗なら「管理者に連絡してください」、処理中なら
  「時間がかかっています」と伝え分ける。
- **説明文の絵文字ロケットを外した** (2026-08): カードに出る実物の
  ロケット (自前の絵) と別のデザインの絵文字が同じ画面にあると
  「同じもの」に見えないため。意味は §5 の説明とツールチップで補う。
- **更新バッジは 3 状態** (2026-08): リリース直後は公開処理 (数分) が
  終わっておらず「更新なし」と判定されるため、楽観的に黄色を点けると
  直後の定期チェックが消してしまい、更新タブに行っても「最新です」と
  出て信頼を失う。✨直後はグレーの「…」(準備中)、公開を確認できたら
  黄色の件数、10 分待っても確認できなければ案内文つきで消灯、の
  3 段階にした (UI レビューの提案)。公開待ちの間は定期チェックが
  バッジを消さない。定期チェック自体も 30 分→10 分に短縮 (他メンバー
  の気づき遅れ対策)。
- **ロケットは #番号の左に統一し、まっすぐ上に飛ばす** (2026-08):
  カードごとの位置推定はレイアウト変更のたびにずれて修正が続いた
  (実際に 2 回発生)。ロケットをタイトル行の左 = 畳んだ行の残骸と
  同じ列に置くと、「起動」タブと同じ画面左端の列に並ぶため、
  **弧を描かずまっすぐ上に飛ばすだけ**でよくなり、基点も完全な
  固定値にできる (ウィンドウ幅・カード枚数・スクロールに非依存)。
  途中で試した「一覧右上の発射台」案は、基点がカードから離れて
  文脈を失うため不採用。破片はロケットが左端にあるので右向きに
  飛ばす (画面外へのクリップ防止)。
- **「承認1 + 却下1」は火も煙も出る複合状態** (2026-08):
  従来は却下が優先で煙だけだったが、承認が付いていることも
  見えるように炎と煙を同時表示する状態を追加 (管理者の指定)。
  煙は 13px の機体に描き込むと等倍で見えないため、機体の左に
  独立した濃いめの粒として置く。また煙は「却下が 1 件ある」という
  状態そのものの表示なので、**演出が走らない経路 (起動時の読み込み・
  定期更新) でも最初から見えている**必要がある (初期 opacity を
  最終値にし、演出は一度きりの揺らぎだけを担当させる)。
- **常駐ロケットはボタン行の右端に右寄せ** (2026-08): ボタン列に
  直接並べると発射・爆発の基点 x がボタン構成 (試すボタンの有無や
  文言の長さ) で変わり座標がずれるため、spacer で右寄せにして
  ウィンドウ幅から x を確定させた。操作ボタンと「状態の絵」の分離
  にもなる。y は一覧描画時にカードごとの行数から推定して記録し、
  2 枚目以降のカードでも自分の位置から発射・転倒する。全状態を
  高さ 36px の固定舞台に載せ、機体と地面の位置がぶれないようにした。
  状態の意味はツールチップで補足 (装飾を「読める部品」にする)。
- **却下取り消し時にローカル記録も掃除** (2026-08): 却下確定→取り消し
  →再確定の 2 周目でも自動で畳めるよう、取り消し成功時に非表示・
  自動畳みの記録 (hidden_prs / auto_folded) を消す。
- **カードの削除・畳みは演出が終わってから** (2026-08): 発射なら
  ✨ が光った直後にカードが一覧から消え、同時に「更新」タブの
  バッジが自動で立つ。爆発なら破片が落ちきってから非表示エリアへ
  畳む。演出の途中でカードが消えると「何が起きたか」が伝わらない
  ため。演出中は該当カードの常駐ロケットを隠し、overlay の機体との
  二重表示を防ぐ。一覧に戻した却下確定カードにはロケットを出さない
  (却下が期日内に取り消されれば状態が変わり、煙付きで再表示される)。
- **却下確定した提出は自動で一覧下の「非表示」へ畳む** (2026-08):
  爆発演出のあと勝手に消えたように見えないよう、下の非表示欄に
  移動して「一覧に戻す」で戻せる。自動で畳んだ記録は
  `local_state.json` の `auto_folded` に残し、本人が「一覧に戻す」を
  押した提出を次回起動時に再び畳み直さないようにする。

### 差分ビューワ (`manager/diffview.py`)

- 「差分」クリックで**既定ブラウザに自己完結 HTML を直接開く** (依存なし・
  難しい画面遷移なし)。フォルダ比較 + 左右並びファイル比較、変更のない行は
  折りたたみ、パスは手元の見え方に合わせ `mgtkit/` 前置。
- **確認用データのダウンロード**は差分ビューワの右上にのみ置く
  (β版タブに置くと誤って使う人が出るため)。クリック時に資料
  「バージョン管理と同時開発のしくみ」4.2 の 3 リスクをイラスト付き
  モーダルで確認してから DL。ZIP (`#N_確認用.zip`) は
  「一式/」(動作チェック用) + 「変更のみ/」(中身チェック用) + 説明 txt。
  **一式に version.json を意図的に入れない** = そのフォルダを ZIP にしても
  マネージャーから提出できず、誤って開発の土台にできない仕組み。
- **確認用 ZIP の「一式」は「最新の正式版 + この提出の変更」の重ね合わせ**
  で作る (= 実際のβ版と同じ中身)。提出ブランチの木をそのまま使うと、
  基点時点に存在してその後 main 側で削除・移動されたファイルが
  紛れ込むため (app-manager-spec.md 混入の不具合の原因)。
- **DL ボタンの文言は「β版データ (確認用) をダウンロード」**:
  当初の「更新データ」は更新タブの正式な更新と紛らわしいため、
  中身 (β版) と用途 (確認) が伝わる名称に変更。
- **差分の配色は意味と 1 対 1**: 赤 = 変更前 (変更行の左)、
  緑 = 変更後・追加、紺 (薄い紺 + 取り消し線) = 削除された行。
  当初は変更行の左と削除行が同じ赤で「赤 = 削除」の凡例が不正確だった。
  凡例は「赤・緑・紺」の漢字一字で統一。
- **ファイルごとの変更説明はファイル名と同じ行の右横**に表示
  (フォルダ比較・ファイル比較とも)。段を分けると一覧が縦に伸びるため。

## 更新が「展開中...」のまま失敗する不具合の修正 (2026-08)

アプリ (本体の画面) を開いたまま「更新して起動」を押すと、更新が
「展開中...」のまま進まなくなる不具合があった。原因と対策:

- **原因**: 本体のサーバーはアプリのフォルダ (`stable/mgtkit/`) の中で
  動いているため、Windows ではそのフォルダが「使用中」になり削除できない。
  さらに従来の置き換え方式 (先に全部消してからコピー) は、失敗すると
  **途中まで消えた壊れた状態**が残った。サーバーはマネージャーを閉じても
  動き続けるので、マネージャーを入れ直しても毎回同じ失敗になる。
  エラーは画面の小さい文字にしか出ず、ログには何も残らなかったため
  「止まったまま」に見えた。
- **更新の前に起動中のアプリを自動で終了する** (`launcher.stop_app`)。
  ポートの使用プロセスを調べて終了させる方式にした。マネージャーが起動
  プロセスを覚えておく案は、マネージャーを再起動すると前回起動した
  サーバーを止められなくなるため選ばなかった。誤終了を避けるため、
  ポートを python 以外のプログラムが使っている場合は終了させない。
  なお終了はどのみち必要 (起動したままだと更新後もポートが使用中で、
  「更新して起動」が古い画面を開き直すだけになる)。
- **フォルダの置き換えは「新しい内容を先に用意 → 名前の付け替え」方式**
  (`installer._replace_dir`)。付け替えに失敗しても元のインストールが
  無傷で残り、平易なメッセージのエラーになる。
- **更新・起動まわりの失敗はログにも記録する** (`log.exception`)。
  画面の文字だけだと今回のように原因調査ができないため。

としての本体はルート直下、という整理に基づき、**アプリマネージャー関係の

## リリース手順 (Phase 4 自動化までの暫定運用)

- `.github/workflows/release.yml`(手動実行)で安定版/β版を Releases に登録する。
  GitHub の Actions タブ → release → Run workflow でバージョン(vX.Y または
  vX.Y-beta.N)とリリースノートを入力する。
- version.json の生成と配布 ZIP(開発用ファイル除外)の添付はワークフローが行う。
  vX.Y-beta.N はプレリリースフラグ付きで登録される。
- Phase 4 で「PR マージ → 自動タグ付け・自動リリース」に置き換える際も
  この ZIP 作成手順を流用する。
- **承認待ちのβ版があるときに手で正式版を出さない。** メンバーの提出の行き場が
  なくなり、承認フローが壊れる。正式版の発行は承認が片づいてから。
- **アプリマネージャー (`manager/`) だけの変更に正式版の発行は不要。** 配布経路が
  2 系統あり、本体(ルート直下)は Releases 経由でアプリが自動更新するのに対し、
  マネージャーは起動 bat の `git pull` で届く。release.yml の配布 ZIP は
  `manager/*` を除外している(-x リスト)ため、発行しても中身が入らない。

## 承認タブの体感速度の改善 (2026-08)

承認タブの「一覧を取得」やボタン操作が遅い原因は、1 回のクリックの裏で
gh コマンド (プロセス起動 + GitHub への往復、1 回 0.3〜1 秒) を直列に
何回も呼んでいたこと。特に一覧取得は PR ごとに `pr view` を繰り返す
N+1 構造で、承認ボタンは「事前確認 → 承認 → 自動リリース判定 → 再描画」
の各段階がそれぞれフル取得していた。対策と、そうした理由:

- **一覧は `gh pr list` 1 回で取得**: レビュー・検証結果・コメントも
  `pr list` の JSON フィールドで一括取得できるため、PR ごとの `pr view` を
  やめた。GraphQL の直接呼び出しはしない (gh の JSON で足り、
  クエリの保守を増やさないため)。
- **キャッシュは「起動中ほぼ変わらないもの」だけ**: 自分のログイン名
  (起動中に不変) は初回のみ、collaborator 一覧は 10 分キャッシュ。
  PR・レビュー・検証の状態はキャッシュしない —— 「状態は GitHub を真実と
  する」原則のとおり、承認・リリースの判定は操作時点の取得結果で行う。
  取得失敗はキャッシュしない (復旧したら即座に直るように)。
- **起動時の先読みはこの 2 つに限定**: 「前処理を起動時に集約」は
  状態系のデータには不適 (操作時には古くなり結局取り直す) ため、
  不変系のキャッシュを起動時に裏で温めるだけにした。
- **承認時の自己承認チェックは一覧取得済みの提出者名を使う**
  (`reviews.approve(author=...)`): 提出者は後から変わらないため安全。
  author 未指定時は従来どおり取得して確認するフォールバックを残した
  (UI 以外からの呼び出しの安全網)。
- **自動リリース判定に使った一覧を再描画に使い回す**: 承認直後は
  「判定用の取得」と「再描画用の取得」で同じ一覧を二度取っていたのを
  1 回にした。リリース実行時だけは一覧が変わるため取り直す。
- リリース時のリリースノート自動生成 (Claude API 呼び出し、数十秒
  かかることがある) は今回は変えない: リリースは頻度が低く、
  待ち時間よりノートの品質を優先する。

### 第 2 弾: 「取得を待たせない」構造への変更 (同月)

往復回数の削減後も「ボタンを押してから取得が始まる」構造のため体感
2〜4 秒残った。抜本策として、取得を速くするのではなく**ユーザーが取得を
待たない構造**へ変えた (`manager/reviewcache.py` + main.py の描画分離):

- **前回結果の即時表示 + 裏で更新 (stale-while-revalidate)**:
  一覧のスナップショット (提出一覧 + リリース一覧 + 自分のログイン名) を
  メモリ一次・`<install_root>/reviews_cache.json` 二次で保持し、タブを
  開いた瞬間・更新ボタンを押した瞬間は手元の内容を即描画して
  「前回の内容を表示中 (n 分前の取得)。最新を確認しています...」を添え、
  裏の取得完了で差し替える。スナップショットは PR タイトルや
  レビュー状態などチーム共有済みの情報のみで、トークンは含まない
  (「トークンを保存しない」方針はそのまま)。
- **整合性の線引き**: 表示は古くてよいが、**判定は操作時点のデータのみ**。
  リリースはもともとサーバ側で承認数・却下を再検証しており、自己承認
  チェックの提出者名は不変なので、古い表示から操作しても安全側に倒れる。
  自動リリースの判定だけは仕組み上もキャッシュから発火しない
  (承認直後に取得した最新一覧でのみ評価する)。ローカル記録の掃除・
  却下確定の自動畳みも最新データの描画時のみ行う。
- **応答の追い越し防止**: 取得開始時に通し番号を採番し、後から届いた
  古い応答は破棄する (連打・定期更新との競合で古い内容に戻らない)。
- **定期ポーリングとの統合**: 30 分ごとの更新チェックを件数だけの
  `count_pending` からスナップショットのフル取得に一本化し (削除)、
  更新バナー・タブバッジ・承認タブの表示を同じ結果から更新する。
  β版タブを開いたときにも裏で再取得する。ポーリングの高頻度化
  (タブ表示中だけ 60〜90 秒) は見送り: タブ切替時の再取得で実用上
  足りており、レート制限や複雑さを先に増やさない。
- **取得の並列化**: 一覧とリリース一覧をスレッド 2 本で同時に取得
  (直列で足し合わせない)。
- 更新ボタンの文言は「一覧を取得」から「最新の状態に更新」へ変更
  (開いた時点で一覧は出ているため、役割が補助的になった)。
- さらに速くする案として GraphQL 1 クエリ化・`gh auth token` による
  HTTP 直叩きも検討した。GraphQL 化はフォールバック付きなら
  リスクを増やさないため第 3 弾で採用 (下記)。HTTP 直叩きは見送り:
  メンバーの PC が社内プロキシ / TLS 検査環境の場合、gh は通るのに
  Python 側の通信だけ失敗する事故があり得る。Git に詳しくない
  メンバーの画面で静かに壊れるリスクを、裏の更新が 1 秒か 0.5 秒かの
  差のために取らない (明確な要求が出てから再検討)。

### 第 3 弾: 裏の取得の 1 往復化と、裏の動きの言語化 (同月)

- **GraphQL 1 クエリへの集約** (`reviews.fetch_snapshot`): 承認待ち
  一覧 (レビュー・検証・コメント込み) + リリース一覧 + 自分の
  ログイン名を `gh api graphql` 1 回で取得する。プロセス起動が
  1 回になり、裏の更新が約 0.7〜1.2 秒になる。以前「クエリの保守を
  増やさない」ため見送った判断は、**失敗したら従来経路 (pr list +
  リリース一覧の並列取得) へ自動フォールバック**する構成にすることで
  覆した — クエリが古くなっても壊れず遅くなるだけ、が成立するため。
  応答は gh の `--json` と同じ形に変換してから既存の組み立て処理を
  通し、一覧の出力形式は変えない (テストも同じ基準で通る)。
- collaborator 一覧はこのクエリに**含めない**: 参加承認前のメンバーは
  権限エラーになり毎回フォールバックしてしまう。従来のキャッシュ付き
  取得 (10 分) のままにする。
- **裏の動きの言語化**: 「取得中...」だけでは動いているか分からない
  という指摘を受け、状態行 (グレー) に裏の処理を逐次表示する:
  「前回の内容を表示中 (n 分前の取得)。最新を確認しています...」→
  「最新の提出状況とβ版・リリースの一覧を確認しています...」→
  「最新の状態です (HH:MM 取得)」。フォールバック時は「方法を変えて
  確認し直しています...」、承認・却下・取り消しの送信中も
  「#N の承認を送信しています...」等を表示する。完了時に取得時刻を
  残すのは「いつ時点の情報か」を常に示すため。

### 第 4 弾: 承認・却下の 0 秒化 (楽観的更新、同月)

承認・却下ボタンは「押した瞬間に済み表示 (バッジ・点火/煙の演出) へ
切り替え、送信は裏で行う」楽観的更新にした。

- 判定は従来どおり送信後の最新データで行う (自動リリースは承認送信後の
  取得結果でのみ発火。楽観的表示からは発火しない)
- 送信に失敗したら、直後の再取得で表示が自動的に元へ戻り、状態行に
  エラーを表示する (画面上の見た目だけが先行し、記録は GitHub が真実の
  原則は崩れない)
- 却下理由の未入力チェックはダイアログを閉じる前に画面側でも行う
  (サーバ側の必須チェックは安全網として残置)

### 第 5 弾: 「押した瞬間に必ず画面が反応する」の全画面への徹底 (同月)

「人は反応がないと何回もクリックする」という管理者の指摘を受け、
承認タブ以外も含む全ボタンで「先に表示を反応させ、重い処理は裏へ」を
徹底した。方針と理由:

- **共通ルール**: ボタンを押したら (1) そのボタンを無効化し (2) 進行中の
  文言を出してから (3) 裏の処理を始める。失敗したらボタンを戻して
  再試行できるようにする。二度押しは「同じ処理が二重に走る」事故
  (二重インストール・修正ループの二重起動など) の元のため、文言だけ
  でなく無効化までをセットにした。
- **ダイアログの確定ボタン** (取り下げ・却下・フィードバックの
  送信/保存/削除): 押した瞬間にボタンを無効化し、エラー表示欄に灰色で
  「送信しています...」等を表示 (dialog_busy/dialog_error)。ダイアログを
  即閉じる案 (楽観的更新) にしなかったのは、これらは失敗時に入力内容へ
  戻す先がダイアログ内にしかないため (承認・却下の楽観的更新とは違い、
  入力テキストを失わないことを優先)。
- **カード上のボタン** (β版を試す・差分・統合・取り消し): 押した瞬間に
  そのカードの操作ボタンをまとめて一時無効化 (_freeze_card)。統合待ち
  カードには元から無効のボタンがあるため、一律有効化ではなく個々の
  無効状態を覚えて復元する。
- **この PC 内だけの操作 (畳む・一覧に戻す) は取得しない**: 手元の
  スナップショットで一覧を描き直すだけ (_rerender_local)。ネットワークの
  取得を挟むと表示の反応が数秒遅れるうえ、リモートの状態は何も変わって
  いないため取得自体が不要。
- **統合のキャンセルも裏へ**: ダイアログを先に閉じてから後片付け
  (統合のやり直し準備) を裏で行う。唯一 UI スレッドで同期実行して
  いた箇所で、環境によって数秒固まる可能性があった。

### 第 6 弾: 表示だけでは連打を止めきれないので札を持つ (同月)

実機の記録を調べたところ、**却下 1 回のつもりが GitHub に 2〜3 件の
差し戻しとして登録されていた** (提出 #33。同じ本文が数秒以内に複数件)。
却下の確定ダイアログだけ「押した瞬間の無効化」が抜けており、押しても
画面がすぐ変わらないため連打されていた。しかもこの重複は、却下確定の
時刻を押し直すたびに更新するため、**自動削除までの残り日数を毎回
振り出しに戻していた**。

- **表示による抑止 (無効化・カードの描き直し) だけでは不十分**:
  どちらも「押した後」に効くため、押した直後に届いた 2 回目の
  クリックは素通りする。承認・取り消しは楽観的更新でボタンごと
  差し替わるので実害が出にくかっただけで、作りとしては同じ穴だった
- **対策は札 (`manager/uiguard.py` の ActionGuard)**: 提出番号を鍵に、
  送信を始める前に札を立て、終わったら (成功・失敗どちらでも finally
  で) 下ろす。札が立っている間の操作は捨てるので、表示がどう出ていても
  実際の送信は 1 回に保たれる。承認・却下・承認/却下の取り消し・
  最新版との統合に適用
- **札は「提出への状態変更」だけで共有する**: 承認と却下と取り消しは
  同じ提出に対する互いに排他の操作なので、1 つの鍵を共有してよい。
  フィードバックの送信など性質の違う操作まで同じ鍵にすると、
  送信中に承認できなくなるため別扱いにする
- **断ったときは黙らない**: 捨てるだけだと「効いていない」と見えて
  さらに連打されるため、「前の操作を送信しています。少し待って
  ください。」を出す
- **画面部品に依存しない別モジュールにした理由**: flet はテストの依存に
  入れていない (CI も同じ) ため、main.py に置くとテストが常にスキップ
  される。切り出したことで連打・並行の挙動を CI で確かめられる。
  main.py 側の適用漏れは、構文木を読むテストで見張る
  (`test_manager_uiguard.py`。提出への操作を足すときは一覧に追加する)
- **同時に直した取りこぼし**: 「登録してはじめる」(保存を裏へ)、
  提出タブの「確認」(取得中はボタンを無効化)、承認の手元データが無い
  経路 (進行中の文言がハンドラーではなく裏の処理側にあり、押した瞬間に
  何も出ていなかった)

### 第 7 弾: 押す前に飛び立った取得が、押した後の表示を巻き戻す (同月)

実機で「承認を取り消す」を押すと **承認 → (一瞬) 承認を取り消す →
承認** と表示が往復する、という報告。原因は競争状態:

1. タブを開いた瞬間に一覧の取り直しが始まる (1 秒前後かかる)
2. その 1 秒の間にボタンを押すと、楽観的更新で画面は正しく切り替わる
3. **押す前に始まっていた取得**が着陸する。中身は「押す前の状態」なので
   画面が元に戻る
4. 送信後の取り直しが着陸してようやく正しくなる

- **通し番号は取得どうしの前後しか見ていなかった**: `reviewcache` の
  `seq`/`applied_seq` は「古い応答が新しい応答を上書きしない」ための
  もので、**利用者が操作したという事実は番号に入っていなかった**。
  そのため操作前に離陸した取得は「古い」と判定されず採用されてしまう
- **対策は操作した時点で番号を進める** (`reviewcache.note_local_change`)。
  楽観的更新の直前に呼ぶと、飛行中だった取得は `put()` で捨てられ、
  操作の後に始まった取得だけが反映される。承認・却下・取り消しに適用
  - 選ばなかった案: 取得中は操作を止める (押せない時間ができて
    「反応しない」に逆戻り)。着陸した取得と手元の変更を突き合わせて
    差分適用する (どのフィールドが自分の操作由来か判別が要り、
    状態が増えるわりに得るものが同じ)
  - 副作用: 捨てられた取得の回では更新チェックも飛ぶ。次の定期実行
    (10 分) かタブを開いた時に拾い直すため実害なしと判断した
- **楽観的更新は番号で引き直した dict に当てる** (`reviewcache.pending_of`)。
  スナップショットは取得のたびに新しい dict へ入れ替わる一方、画面は
  内容が前回と同じなら一覧を作り直さない (押した瞬間のクリック取り
  こぼし防止)。この組み合わせで**ボタンが古い dict を掴んだまま**に
  なることがあり、そこを書き換えても最新には乗らない。今回の報告とは
  別の、まだ表に出ていなかった穴

## 更新タブの廃止と自動更新 (2026-08)

「承認されたものは自動でリリースされるのだから、更新は手動操作でなく
自動でよい」という管理者の判断で、タブを**起動 / 更新版を提出 /
β版の確認と承認**の 3 つにし、正式版の取り込みを自動化した。

- **自動更新のタイミング**: 起動時と 10 分ごとの定期チェックで新しい
  正式版を見つけたら自動で取り込み、起動タブに黄色いタグ
  「バージョンが更新されました (vX.Y)。」と更新内容を表示する。
- **アプリ起動中は取り込まない**: Windows では起動中のアプリの
  フォルダが使用中で置き換えられず、勝手に終了させると作業を壊す
  ため、「次回の「起動」で自動的に更新されます」と案内して予約し、
  次の「起動」ボタン押下時に (どうせ再起動する流れなので) 終了 →
  更新 → 起動する。
- **過去の更新ログ**: 起動タブのグレーのボタンからダイアログで
  版ごとの日付・更新内容を一覧し、「ZIP を保存」でその版の配布 ZIP を
  ダウンロードフォルダへ保存できる (Releases から取得するだけなので
  マネージャー側に過去版の保管は持たない)。誤って古い版を上書き
  インストールする事故を避けるため「この版に戻す」ボタンは付けない
  (必要になったら管理者操作として検討)。
- リリース後の「準備中」表示は更新タブのバッジから起動タブの文言に
  移し、公開を確認できたらそのまま自動更新につなげる。

### UI レビューでの決定 (更新タブ廃止の 1〜2 巡目)

- **使用中のアプリを黙って終了しない**: 取り込み待ちの版がある状態で
  「起動」を押したとき、アプリ使用中なら確認ダイアログ
  (「更新して開く / あとにする」) を挟む。理由 = 通常の「起動」は
  開いている画面を開き直すだけなので、同じボタンが無警告で入力中の
  作業を消す挙動に化けるのを防ぐ (レビュー最優先指摘)。
- **「起動」ボタンの位置は固定**: 版情報 → ボタン行 → 通知 → 更新内容の
  順に並べ、通知の有無でボタンが上下しないようにする。空の案内行は
  行ごと畳む (余白のガタつき防止)。
- **手動の「最新の状態に更新」と確認時刻の常時表示を残す**: 自動化しても
  「管理者に言われて今すぐ取り込みたい」「失敗後に再試行したい」が
  成り立つように。無言の画面は「最新」と「壊れている」を区別できない
  ため、「最新の状態です (HH:MM 確認)」を常時出す。
- **黄色いタグは維持**: 完了通知としては緑が素直という指摘はあったが、
  管理者指定の黄色いタグ (「バージョンが更新されました」の目立ち方) を
  優先。文言は次の行動が分かる形にした
  (「アプリを vX.Y に更新しました。このまま「起動」してお使いいただけます。」)。
- **更新内容は常設化**: 黄色タグは一過性 (起動したら畳む)、
  「いま使っている版 (vX.Y) の更新内容」は常設にして役割を分離。
  リリースノート先頭の「vX.Y リリース。」は版名見出しと重複するため
  表示時のみ除去する。
- 過去の更新ログは目的の一文 (提出済み計算書の当時の版での再現) と
  「直近 30 件まで」の但し書きを付け、内容は 2 行に畳んで行タップで
  全文表示。保存結果はスクロール外に固定表示する。

### 実機フィードバックでの追加決定 (同月)

- **内容が同じなら一覧を作り直さない** (`_render_state` の指紋比較):
  タブを開くと即時表示の 1〜2 秒後に裏の最新取得が一覧を作り直すため、
  ちょうど押そうとしたボタンが別のコントロールに差し替わり、クリックが
  取りこぼされる競合があった (「非表示⇄一覧に戻す」が 2 回押さないと
  効かないように見えた原因)。表示内容 (提出一覧・β版・非表示状態) の
  指紋が前回描画と同じときは一覧を触らず、状態行だけ更新する。
- **手動の「最新の状態に更新」ボタンは廃止**: 「タブに来る = 最新が
  見たいとき」という管理者の判断で、タブ遷移時の自動更新 (即時表示 +
  裏で取得) に一本化。UI レビューで追加した手動確認の導線は過剰だった。
  「最新の状態です (HH:MM)」の状態行だけ残す (生存確認のため)。
  起動タブもタブに戻った瞬間に更新チェックが走る。
- **ボタンのアイコンは「行の主要ボタン + 動作を表すもの」に統一**:
  色付きの主要ボタン (起動・ZIP を選んで提出・β版を試す・
  自動修正を試す) はアイコン付き、枠線の補助ボタン (過去の更新ログ・
  確認・非表示など) は文字のみ。例外は「ZIP を保存」のダウンロード
  アイコン (⬇。保存という動作が一目で伝わるため管理者の指定で残す)。
- **版の呼び方は「現行版」に統一** (「いま使っている版」は冗長のため
  管理者指示で変更): 起動タブの見出しは「現行版 vX.Y (最新)」とし、
  「(最新)」は最新であることを確認できたときだけ付ける (取り込み
  待ちで古い版のまま「最新」と出さない)。過去の更新ログの緑ラベル・
  更新内容の見出しも「現行版」に揃える。
- **公開待ちの見せ方** (ロケット到着後): ロケットは「起動」タブの
  ラベル位置へ着地し、キラッの後に起動タブへ黄色バッジを点け、
  同色の黄色タグで「新しい正式版を準備中です (数分かかります)。
  公開されると自動で更新されます。」を表示する。タグ右端の丸矢印で
  今すぐ確認でき、押すたびに「更新の確認: HH:MM (公開待ち)」の
  時刻スタンプが更新される (待っている人に動いていることを見せる)。
  バッジ・タグは更新の取り込みが完了した時点で消す (完了の黄色タグに
  置き換わる)。

## 過去の更新ログの図 (モック) の決定 (2026-08)

「誰がどの版を基に開発してどこで正式版になったか」を Git を知らない
メンバーにも伝える時系列図。実装前にモックで見た目を確定した
(`manager/docs/mockups/history_flow.html`。UI レビューは厳しさ MAX で
2 巡 + 仕上げ 1 巡)。

- **図の文法**: グレーの本線 = 正式版の列 (白丸 = 版、大きい紺丸 +
  橙リング = 現行版)。人ごとの色の帯 = 提出された更新 (左端 = 提出日)。
  本線から降りる線 = その版から派生、本線へ上がる矢印 = 公開。
  点線の帯 = まだ確認中 (きょうの線まで)。ブランチ・マージ・PR という
  言葉は一切出さない。
- **選ばなかった案**: 曲線だけの一般的な Git グラフ風 (どの版から
  派生したかが読み取りにくい)、縦時間軸 (ガントに慣れた設計者には
  横軸 = 時間が自然)。
- **斜め線は 60° に統一**し、折れ角は滑らかなカーブでつなぐ (管理者
  指示。鋭角の折れ線は硬い印象のため、最後の縦 24px を三次ベジェで
  水平へつなぎ矢先の根元に収める)。
- **時間軸は 42px/日の等縮尺**。存在しない期間 (初回配布より左) は
  描かない。同じ版から複数の提出があるときは上下レーンに分ける
  (基本は下、2 人目から上)。
- **情報の重複を作らない**: 帯 = 名前 + 番号 + 概要、ホバー = 基点と
  公開日と保存ボタン、一覧 = 全文 + 日付、と役割を分ける。
- **今後の方向 (合意済み・未実装)**: 更新どうしが同じ箇所を変更して
  重なった (コンフリクトした) 場合は、図に ◆ (琥珀色) で自動調整の
  点を示し、一覧の行から開く「更新内容」画面に AI が自動調整した
  内容を琥珀色の枠で色分けして残す
  (`manager/docs/mockups/history_conflict_note.html`)。

## 過去の更新ログの図の実装 (2026-08)

モック (`manager/docs/mockups/history_flow.html`) を Flet に実装した。
描画は `manager/historyview.py` (canvas)、データの組み立ては
`manager/history.py` (描画に依存しない純ロジック、テスト対象)。

- **正式版⇔提出の対応付けはサーバに記録を持たない**: 正式版 (release) と
  取り込み済みの提出 (merged PR) を「公開日以前で最も新しい取り込み」で
  新しい順に貪欲に対応付ける。マネージャーの運用では取り込み→数分で
  リリースなので日付で安定する。対応が付かない最古の版 = 初回配布。
  選ばなかった案: リリースノートに提出番号を埋め込んで対応付ける
  (過去のリリースに遡って効かない・ノートの文面に運用依存が生まれる)
- **基点 (どの版から作ったか) は提出日から推定**: 提出日以前で最も
  新しい正式版。作った瞬間の記録は Git 側にしか無いが、運用上は
  提出時点の最新版から作るためこれで一致する
- **レーン割当は派生線も含めた範囲で判定**: 帯そのものだけで判定すると
  基点ノードから帯まで横に走る派生線が他の帯を突っ切るため、
  「基点の日〜終わりの日」で重なりを見る。端の日が同じだけ (前の帯の
  公開日 = 次の帯の基点) は重なり扱いしない (連続する提出が交互に
  レーンを変えないため)。3 つ以上重なったら下 2 段目へ (図の高さも拡張)
- **ZIP 保存の置き場所**: 図の中には置かず、帯・ノード・一覧の行を
  クリックした先の「更新内容」画面に置く (管理者指示 2026-08。
  図はダウンロードアイコンを持たない)。一覧の行の ZIP ボタンは
  よく使う近道としてそのまま残す
- **AI が自動で調整した箇所の色分け**: リリースノートに
  「AI が自動で調整した箇所」という見出し行があれば、そこから後ろを
  琥珀色の枠で表示する (更新内容の画面と起動タブの常設欄の両方)。
  ノート側にこの見出しを書き込む処理は今後のコンフリクト自動調整の
  実装時に追加する
- **canvas の文字**: Flet canvas の Text は page.theme のフォントを
  継承しないため、図の描画時にフォント名を明示する (同梱 IPA フォント
  環境での豆腐化対策)。文字幅は概算 (和文=全角) で、入り切らない帯は
  ラベル外出し + 塗りを濃くする (ガント図の短いバーの流儀)
- **済み提出は「直近 n 件」だけで拾わない** (2026-08 修正): 図の元に
  していた取り込み済み PR は「更新の新しい順に 40 件」だったが、この
  リポジトリには提出 (feature/) 以外の PR (管理者によるマネージャー
  自体の更新) が短期間に大量に入るため、古い提出が窓から押し出されて
  正式版の提出者・帯が消えた (実際に v1.1 = 提出 #31 が「—」になった)。
  ブランチ名で提出だけを絞り込む検索 (`head:feature/`) を足し、
  直近 n 件との和集合を使う (`reviews.merged_submissions_query`)。
  - 直近 n 件を残す理由: 検索の索引付けには遅れがあるため、公開直後の
    版はこちらで確実に拾う。両方に出る提出は番号で 1 件にまとめる
  - 選ばなかった案: 件数を 100 に増やすだけ (同じ勢いで PR が増えれば
    1 週間ほどでまた消える)。正式版のタグのコミットから対応する PR を
    引く (対応付けとしては厳密だが、リリースごとに問い合わせが増える)

### 実機フィードバックでの調整 (同月・図の簡素化とサイズ可変化)

- **ウィンドウサイズは固定値をやめて可変に**: 起動時に現行版の
  リリースノートの最長行が折り返さない幅・全行が入る高さへ合わせる
  (上限 1240x1000、下限 760x640。起動時 1 回だけで、手でのリサイズは
  妨げない)。過去の更新ログのダイアログはウィンドウの約 8 割とし、
  図の下に公開済みの行が少なくとも見える高さを確保する
- **図から消したもの** (管理者指示「不要な情報は消す」):
  左側のレーン見出し (時期・提出された更新・正式版)、
  帯の中の # 番号以降のタイトル文 (帯は「名前 #番号」だけ。内容は
  ツールチップ・一覧・更新内容の画面が担う)、
  必要数の却下がそろった提出 (承認タブでも既定非表示のもの)
- **凡例は文章をやめてアイコンに**: 図と同じ見た目のミニ図形
  (丸・リング付き丸・派生・公開・点線帯) + 最小限の言葉。
  長文の「読み方」は図の文法がアイコンで伝わるため廃止
- 時系列図は縦をのびのびさせるため本線を y=180 に下げ、上下レーンの
  間隔を広げた (図の高さ 330px + 深いレーン分)
- **線の見た目は Git グラフの定番に寄せた** (管理者指示で 60° 直線を
  廃止): 派生はノードを水平に出て S カーブで帯へ、公開は帯の右端から
  少し水平に出てから浅い角度 (約 22°) で本線へ滑らかに合流する。
  参考にした公開実装: gitgraph.js (MIT・こうした「Git グラフ」描画の
  定番。現在はアーカイブ済みで、後継の定番は Mermaid の gitGraph)。
  本線は枝より太くして主従の強弱を付ける
- **帯はラベルが入る幅に可変**: 「名前 #番号」が入らない日付幅の
  帯は左へ (公開済み) / きょう線を右へ押して (確認中) 広げる。
  現行版 → きょう線のマージンは等縮尺を崩してよい (管理者指示)。
  そのため週グリッドは最新版の位置までで止める
- **ゼロから作る前に公開実装を探す運用を追加** (ui-review-loop
  スキルと manager/CLAUDE.md に記録): 定番がありそうな UI は OSS を
  探して慣習を借りる。トークンと手戻りの節約のため
- **現行版バッジの置き場所は自動で選ぶ**: 基本はノードの上。現行版から
  上レーンへ枝が出ていれば下、上下ともふさがっていればノードの右
  (本線の上) に置く (枝の線と文字が重ならないようにするため)
- **きょうの線は波線**: 確認中の帯の破線と紛らわしいため破線をやめた
- **帯は全部コンパクトな箱に統一** (実機フィードバック): 期間いっぱいに
  伸ばすのをやめ、どの帯も「名前 #番号 + 同じマージン」の大きさで
  合流 (きょう) 側に寄せる。期間は枝の線の長さが表す。
  きょうの波線の手前には帯・バッジとも 16px のマージンを必ず取る
- **基点の推定は時刻まで比較する** (実データで取り違えを確認):
  #83/#84 は v1.1 公開と同じ日の公開前に作られており、日付だけの
  比較だと v1.1 ベースと誤表示された (git の merge-base では v1.0)。
  リリースの公開日時・提出の作成日時を時刻付きで持ち、
  「公開日時 ≤ 作成日時」で基点を選ぶ。正式版⇔取り込みの対応付けも
  同様に時刻で比較する。それでも「公開後に古い版から作った」ケースは
  日時では見抜けないが、運用上まれなので許容 (厳密にやるなら
  提出ごとに分岐点の問い合わせが必要で、一覧表示が重くなる)
- **基点は推定ではなく分岐点コミットの事実で出す** (時刻比較でも実データ
  で外れたため): 提出は手元のアプリの版から作られるので、「公開の後に
  古い版の内容が提出される」のが普通にある (=作成日時からは分からない)。
  承認待ちの提出は件数が少ないため、1 件ずつ分岐点 (merge-base) を
  問い合わせ、リリースタグの commit と突き合わせる。取得に失敗した
  提出と取り込み済みの提出 (件数が多く往復が高くつく) は従来どおり
  日時から推定する
- **図は開いたままでも最新に追い付く** (実機で古い基点表示が残った件):
  ダイアログは手元のスナップショットを即表示した後、裏で必ず最新を
  取得し、図に効く内容が変わっていたら開き直す (変わっていなければ
  触らない)。あわせて、(a) GraphQL が使えず従来経路に落ちたときも
  タグの commit 対応表を取得して分岐点照合が効くようにし、
  (b) 取り込み済みの提出にも分岐点を付ける (分岐点は変わらないため
  「番号:headSHA」で記憶して再問い合わせしない)

## リリースノートを提出時の PR 本文から転載する方式へ変更 (2026-08)

きっかけは API 利用量グラフの確認。リリース時のリリースノート自動生成
(Claude API) が管理者のキーで課金されており (v1.1 で約 $0.03)、内容も
提出時に生成済みの PR 本文の書き直しだった。「承認タブの体感速度の改善」の
節で「品質優先で変えない」としていた判断を、次の理由で見直した:

- **必要な情報は提出時点で全部そろっている**: PR 本文 (提出者のキーで
  生成済み) に更新内容も制限事項も書かれており、リリース時にもう一度
  AI に書かせる必然性がない。書き直しの価値は「制限事項の括り出し」
  程度で、それは提出時の様式で担保できる
- **様式を提出時の約束にした**: `claude_helper.generate_pr_body` の様式に
  「## ご利用にあたっての制限事項」(該当なしなら「- なし」) を必須で追加。
  「## 更新内容」とこの節は、リリース時に `reviews.release_notes_from_pr`
  が**機械抽出でそのまま転載**する (API 呼び出しなし・待ち時間なし)。
  レビュー担当者向けの節 (影響範囲・変更ファイルの説明・注意・
  提出時の警告) は利用者向けノートには載せない
- 様式に沿わない本文 (手書きの PR 等) は従来どおり定型文
  「vX.Y リリース。+ タイトル」へフォールバックする
- 選ばなかった案: (1) リリース確認時に「AI で整形する (数円)」を
  選ばせる — 選択肢が増える割に、様式で品質が足りる見込みのため見送り。
  (2) β版 (prerelease) のノートを転用 — β版のノートは
  「提出 #N の検証通過版です」の定型 1 行で、リリースノートの材料に
  ならない
- 補足: リリース直前に PR 本文を GitHub 上で手直しすれば、そのまま
  リリースノートに反映される (AI 生成時代にはできなかった調整手段)
- **手書き提出でも様式が揃うようにした** (同じ変更の第 2 弾):
  提出タブの入力を「更新内容」「ご利用にあたっての制限事項」の
  2 項目にし、それぞれに薄いグレーの記入例 (placeholder) を常時表示。
  AI (キー登録) なしの提出でも PR 本文が様式どおり組み立てられ
  (`submit.fallback_pr_body`)、リリースノートの機械抽出につながる。
  記入欄に Material のラベルを使わなかったのは、未フォーカス時に
  ラベルが欄内に座って記入例 (hint) が隠れる仕様のため
  (項目名は欄の上の見出し行に出す)。手書きの制限事項は AI 生成時にも
  プロンプトへ渡し、生成結果の制限事項の節へ必ず反映させる
- **API を使う自動生成は提出時に本人が選ぶ方式へ** (同・第 3 弾):
  更新内容・制限事項の両方が空欄のときだけ、提出確認ダイアログで
  「空欄のまま提出 (無料・既定)」「Claude で自動作成 (数十円ほど)」を
  選ばせる。どちらか手書きがあれば手書きを採用して API は使わない。
  理由: 本人が選ばない限り API 使用料を発生させない (管理者指示。
  発端は「使った覚えのない利用料」の調査)。既定を無料側にしたのは
  同じ理由から。キー未登録の PC では選択肢自体を出さない
  (自動生成できないため空欄提出のみ)。
  空欄のまま提出された提出は、正式版のリリースノートも空欄にする
  (Releases 上は「vX.Y リリース」の見出しだけになる)。
  従来のフォールバック定型文「vX.Y リリース。+ タイトル」をやめたのは
  管理者の「空欄でいい」の指示による

## 提出の記入欄をタブから確認ダイアログへ移す (2026-08)

管理者指示。提出タブには「ZIP を選んで提出」だけを置き、ZIP を選んだ
あとの確認ダイアログで「Claude で自動作成する (推奨)」「自分で入力する
(無料)」を選ばせる。手入力を選ぶと同じダイアログの中に記入欄が出る。

- **なぜタブから移したか**: タブに常設していた記入欄は、提出のたびに
  「何を書けばよいか分からないまま空欄で通過される」入口になっていた。
  ZIP を選んだ後なら件数が確定していて、書く材料がそろっている
- **選択肢は「空欄提出」ではなく「自分で入力する」にした**: 従来は
  「空欄のまま提出 (無料)」だったため、無料を選ぶと説明の無い正式版が
  生まれていた。更新内容が空欄の提出はリリースノートも丸ごと空欄になる
  (`reviews.release_notes_from_pr` は「## 更新内容」が無いと None) ため、
  手入力を選んだときは**更新内容を必須**にして空欄提出の道を塞いだ。
  制限事項は空欄可 (PR 本文では「- なし」になり、ノートからは節ごと消える)
- **既定は課金側 (自動作成) のまま**: 全提出でこのダイアログが出るように
  なったため、「本人が選ばない限り API 使用料を発生させない」と書いた
  節 (上記「API を使う自動生成は提出時に本人が選ぶ方式へ」) より
  課金の機会は増える。管理者の判断で既定は推奨側に置く。料金は
  「ご自身の API キーで 1 回数十円」と誰の財布かまで画面に書き、
  無料の選択肢を同じ大きさで並べることで担保する
- **自動作成の結果を提出前に見せる** (`main._review_ai_text` →
  `submit.finalize_submission(on_review=...)`): この 2 節はリリース時に
  そのままリリースノートへ転載されるため、本人が一度も読まないまま
  全員に公開されるのを避ける。確認画面で直した文章は
  `submit.body_with_user_sections` で本文の該当 2 節だけ差し替える
  (影響範囲・変更ファイルの説明などレビュー用の節は順序ごと残す)。
  この確認は commit / push より前に行うので、取り消しても GitHub 側に
  ブランチも PR も残らない
- **「提出する」は無効化しない**: 空欄のまま押されたら、その場で記入欄を
  赤枠にして理由を欄の直下に出す。灰色のボタンは押されても無反応で
  連打を招くため (「押しても何も起きないボタンを作らない」の原則。
  GOV.UK Design System / Material 3 / NN/g も無効化しない側を推奨)
- **確認ダイアログのスクロールは条件付きに**: 常に `scroll=AUTO` だと
  短い既定の状態でもダイアログが画面いっぱいに伸びて空白だらけに
  見えるため、確認事項が増える提出 (提出先の選択・削除ファイル・警告)
  のときだけスクロールにする
- 寸法の裏取り: 既定ウィンドウは 760x640 (`_fit_window_to_notes` の下限)。
  手入力を開いた状態のダイアログはこの中に収まる。収まらないのは
  「差し戻し後の再提出 + 削除ファイル + 警告」が重なったときだけで、
  頻度が低いためスクロールを許容する (管理者判断)
- 見た目のモック: `manager/docs/mockups/submit_describe_choice.html`

  (今回のつまずきの記録): 高さ制約が無限のためレイアウトが壊れ、

  Flutter は例外をコンソールに出さない)。行の左右セルは START 揃えとし、
  長い行の折り返しで左右の背景高さが揃わない問題は「折り返し行数を
  文字幅から概算して短い側に改行を足す」方式で解消 (レビュー指摘)
- **ジャンプは概算オフセット方式のまま** (レビュー提案の key 指定
  スクロールは不採用): 仮想化 ListView は未描画の項目へ key 指定で
  スクロールできない (Flutter の制約) ため。折り返し行数の概算を
  高さ計算に使うことで精度は改善した
- **リスクカードの図は canvas で描き直した**: HTML 版の SVG は
  文字 (<text>) を含み、Flet の画像表示 (flutter_svg) は <text> を
  描けないため、同じ座標・配色のまま ft.canvas で再現した (1.5 倍)。
  リスク確認は内容に合わせた高さ (上限 540px) + スクロールで、
  小さいウィンドウでもボタンが画面外に消えない
- **コード欄のフォントは Consolas 指定のまま**: 実機 (Windows) では
  日本語グリフは DirectWrite のシステムフォールバックで描かれる。
  ハーネス (オフライン Web) ではフォールバック先が無いため
  同梱 JP フォントに差し替えて撮影する
- **確認用データの保存はリスク確認ダイアログを挟む**: HTML 版の
  モーダルと同じ 3 枚のカード (文言共通) を Flet で再現し、
  「リスクを理解した上で保存」を押したときだけ ~/Downloads に
  ZIP を書き出す。保存結果はダイアログ下部のステータス行に表示

## 差分ダイアログの高速化 (2026-08)

- **クリック時のネットワーク往復をゼロにする方針** (管理者指示
  「動作は限りなく早い方がいい」): 遅さの正体は表示のたびに直列で
  走っていた 3 回の通信 (作業クローンの全体 fetch → 提出ブランチの
  fetch → 説明文の取得)。以下で解消した
  - 提出の先端 (head_sha) と分岐点 (fork_sha) はスナップショットが
    既に持っているので、両方が手元のクローンにあれば fetch しない。
    無いときだけ 1 回で fetch する (従来の 2 回を統合)
  - 説明文 (PR 本文) はスナップショットに同乗させた (クリック時に
    gh を起動しない)。旧キャッシュに無いときだけ従来どおり取りに行く
  - β タブの一覧を描いたら、裏で各提出の差分モデルを先読みして
    number:head_sha でキャッシュする (最大 8 件)。クリック時は
    組み立て済みを出すだけなので体感ほぼ 0 秒。提出が更新されると
    キーが変わるので自然に作り直される (履歴ダイアログの SWR と
    同じ考え方)
- **分岐点はスナップショットの fork_sha を比較の基点に使う**: fetch を
  省くと手元の main が古いことがあり、ローカルで merge-base を計算
  すると比較の基点がずれる。GitHub 側の真値 (fork_sha) を使えば
  手元の main の鮮度に関係なく正しい差分になる
- **確認用データ ZIP は保存時に組む**: 変更ファイルの中身の取り出し
  (ファイル数ぶんの git 起動) を表示時から保存時へ遅延。ZIP の土台
  (最新の正式版) は保存・ブラウザ表示の直前に fetch して最新化する
  (表示で fetch を省いた分の正しさをここで担保)
- **git 操作は 1 本の鍵で直列化**: 先読みとクリックが同じ作業クローン
  へ同時に git を走らせると壊れるため。先読み中にクリックしても
  その完了を待つだけで、二重に組み立てることはない

## 差分表示を 0 秒にする (2026-08, 実機で 20 秒かかった件)

- **本当のボトルネックは通信ではなく git の起動回数だった**: 変更
  ファイルごとに「変更前」「変更後」を別々の git で読んでいたため、
  25 ファイルの提出で git を 52 回起動していた。Windows は
  ウイルス対策が git.exe を毎回走査するので 1 回 100〜400 ms かかり、
  ファイル数に比例して待ち時間が伸びていた (実機で約 20 秒)
- **中身の取り出しは `git cat-file --batch` で 1 回にまとめた**:
  ファイル数によらず git の起動は一定。表示 52 回 → 3 回、確認用
  データ 86 回 → 2 回になった (Windows で 1 回 300 ms と仮定すると
  表示は 15.6 秒 → 0.9 秒)。**差分の計算方法 (difflib) は変えて
  いない**ため表示内容は 1 行も変わらない (従来方式と行を突き合わせる
  テストで固定した)
  - 採らなかった案: `git diff -U3` の出力を解析する方式。git は 1 回で
    済むが差分アルゴリズムが difflib と別物のため、行の対応が変わって
    表示が微妙に変わる。速度は同等なので安全な方を採った
- **鍵を「提出ごと」に分けた**: 全体で 1 本の鍵にしていたため、
  別の提出を先読み中にクリックするとその完了まで待たされていた
  (むしろ遅くなる場合があった)。読み出し (cat-file/diff/show) は
  並行して安全なので鍵を取らず、書き込み (clone/fetch) だけ直列化する
- **組み立て済みの差分をディスクにも保存する** (`manager/diffcache.py`):
  アプリを開き直した直後のクリックも待たせないため。キーは
  「番号-先端-分岐点」で、内容が変われば必ず作り直す。分岐点が
  分からない提出は手元の状態しだいで内容が変わるので保存しない。
  作業クローンを作り直して中身が取り出せない場合も組み直す
- **先読みは一覧の描画を待たず、データが届いた時点で始める**:
  タブを開いてすぐ押しても間に合うように。初回は作業クローンの
  用意 (数十秒) もここで裏に回るので、使うときには終わっている

- **説明文 (ファイル別の青枠) はディスク保存の対象に含まれる**:
  提出の本文だけを編集した場合、コミットが変わらないためキーも
  変わらず、古い説明が出続ける (従来は再起動で消えていた)。説明は
  提出時の自動生成でほとんど編集されないため許容し、画面にも
  「提出時に自動生成されたもの」と断りを出している
- **まとめ読みが失敗したら 1 件ずつ取り直す**: 失敗を握りつぶすと
  「全ファイルがバイナリ扱い」「中身の無い確認用データ」という
  静かな誤りになるため。確認用データは 1 件も取り出せないときは
  作らずにエラーを出す (空の ZIP を渡さない)

## 開くたびの待ち時間をなくす (2026-08, 実測して判明した続き)

実機と同じ経路で測り直したところ、git の起動を減らした後に残って
いたのは **Python 側の 2 つ**だった (大きめの提出で計測):

- **画面部品の組み立てが 4.4 秒**: 差分 1 行が十数個の部品になるため、
  5340 行では数万個を作ることになる。しかもこれは**キャッシュが
  効いていても開くたびに必ずかかる**。対策は 2 つ
  - 見た目に関係のない入れ物 (行を囲む Container) をやめた。
    見た目は変わらず、行あたりの部品が 5 個から 4 個に減る
  - **見ない行は作らない**: 開いた時点で組み立てるのは 1200 行を
    目安にし、超えるぶんは「この差分を表示」ボタンにして、押された
    ときに組み立てる (画面が止まらないよう裏で組む)。決め方は
    3 つ: 小さいファイル (200 行以下) は目安を超えていてもそのまま
    出す (ボタンだらけにしない)、1 ファイルが巨大なときは目安まで
    出して残りをボタンにする (開いた画面がボタン 1 つにならない)、
    畳んだ差分を展開したら後ろのファイルのジャンプ先も直す。
    ファイル一覧 (＜1＞) には全ファイルが並び、見出しも全部出るので、
    何が変わったかの見落としは起きない (全部まとめて見たいときは
    「ブラウザで開く」が従来どおり全行を出す)
- **差分の計算 (difflib) が 4.9 秒**: これは先読みが裏で済ませるので
  クリック時には効かない。先読みが終わる前に押した場合だけ待つ
- 手元にあるコミットの確認も git 1 回ずつだったので、まとめて
  1 回で調べるようにした (`cat-file --batch-check`)

結果 (変更 12 ファイル・5340 行の提出、Windows を想定して git 1 回
300ms として計測): 先読み済み **0.34 秒**、再起動直後 **0.63 秒**、
先読み前に押した場合 6.3 秒 (改善前は 13.3 秒)

## 画面の更新は必ず画面のループ上で行う (2026-08, 実機の「別の操作をすると表示される」)

- **症状と原因**: 差分ダイアログが「差分を準備しています...」のまま出ず、
  何か別の操作をした瞬間に表示される。遅いのではなく**出来上がった
  画面が送信されていない**のが原因だった。Flet は画面の更新を送信
  キューに積むだけで、積んだ側 (裏スレッド) からは画面の処理ループを
  起こせない。ループは仕事が無いと待ち状態で止まっているため、
  利用者が何か操作してループが目を覚ますまで滞留する
  (デスクトップ版の送信は `asyncio.Queue.put_nowait`。内部で使う
  `loop.call_soon` は別スレッドからだと待ち状態を中断できない)
- **Web 版では出ない**: ブラウザとの通信が常に流れていてループが
  頻繁に起きるため。**デスクトップ版だけで出る**ので、UI レビュー用の
  Web ハーネスでは再現できない (この種の不具合は実機報告が頼り)
- **対策**: 裏スレッドから画面を触るときは `run_ui` (中身は
  `page.run_task` = ループを起こす経路) を通す。加えて、書き忘れても
  取りこぼさないよう `page.update` / `page.show_dialog` /
  `page.pop_dialog` の 3 つを main.py で包み、ループ外から呼ばれたら
  自動でループ上に載せ替える。差分の部品の組み立て自体は裏のまま
  (画面を止めないため)、表示だけをループ上で行う
- **使い分け**: 画面の書き換えが 1 か所で完結するなら `page.update()`
  をそのまま呼べばよい (包んであるので自動でループ上に載る)。
  「書き換えと更新をひとまとめにしたい」ときだけ `run_ui` を使う
  (一覧の差し替え、演出のコマ送りなど。別々にすると、送信側が変更点を
  数えている最中に書き換えてしまう)
- **失敗の伝え方**: 表示をループ上に載せると、呼び出し側の try では
  失敗を捕まえられない。`run_ui(fn, on_error=...)` で同じ状態表示に
  知らせる。差分ダイアログは「組み立て (裏) → 表示 (ループ上)」に
  分けてあり、どちらで失敗しても同じ場所に出る
- **包むときの注意**: 元の関数を控える変数名を、後から定義する
  ラッパーと同じ名前にしないこと (同じ関数内で後から同名を def すると
  参照までそちらに向き、無限再帰になる。実際に踏んだ)
- **ループ判定は画面のループかどうかまで見る**: 単に
  「asyncio のループ上か」だけだと、裏で asyncio を使うワーカーから
  呼ばれたときに誤判定して元の不具合に戻る

## ロケット演出をカードごとの定位置から出す (2026-08, 練習台で洗い出した 4 点)

演出がどう動くのかを確かめたくても、本番は 2 人承認制なのでひとりでは
発射 (2/2) も却下確定の爆発も再現できない。そこで演出だけを抜き出した
練習台 (使い捨て) をひとりで触れる形で作り、そこで見つかった問題を
本体に反映した。以下は**なぜそうしたか**の記録。

### 直した 4 点

1. **基点をカードごとに持つ**。押したカードのロケットからそのまま飛ぶ・
   倒れる。2026-08 に一度は全カード共通の固定点 `(55, 252)` にしたが、
   それだと 2 枚目以降のカードを押しても 1 枚目の位置から飛んでしまう
2. **常駐ロケットの大きさと位置を全状態でそろえる**。承認なしの状態が
   基準で、増えるのは炎と煙だけ
3. **カードが一覧から消えるのは演出が終わってから**。飛んで ✨ と弾ける
   まで、爆発して破片が散りきるまでカードはそのまま待つ。待っているあいだ
   ロケットの場所は空欄 (場所は詰めない)
4. **発射の経路が到達点を追い越して戻ってこないようにする**

### なぜ「固定点」をやめて「カードごと」に戻せたのか

固定点にした理由は「カードごとの位置推定はレイアウト変更のたびにずれて
保守が続いた」から。今回は推定をやめ、**一覧の行の高さをすべて固定値に
した** (`_H_TITLE` / `_H_BADGE` / `_H_TEXT` / `_H_REJECT` / `_H_NOTE` /
`_H_BTNS`)。高さが決まっていれば積み上げで 1px まで正確に出せる。

- Flet には「描画後の位置を問い合わせる」手段がない (0.86 で確認)。
  位置は積み上げでしか求められないため、固定するしかなかった
- カードの高さは**実際に並べた行の合計**から出している
  (`_stack_height`)。高さの表を別に持つと必ず本体とずれるため、
  行を足し引きしても自動で追従する形にした
- 一覧はスクロールするので、`on_scroll` でスクロール量を控えて
  基点から差し引いている
- 実測値は `_LIST_TOP` (1 枚目のカードの上端) の 1 つだけ。ヘッダーと
  タブバーの高さは Flet と OS のフォントで決まり計算では出せないため。
  説明文も高さを固定して、幅で伸び縮みしないようにした

**代償**: 差し戻しの理由が長いと 2 行で切れる (全文はマウスを乗せると
出る)。行が伸びると下のカードの基点がずれるため。統合待ちの案内文も
同じ理由で 2 行まで。

### 常駐ロケットが状態によって縮んでいた理由

スロットの高さが 24 しかなく、炎ぶんを含む高さ 35 の画像が収まらずに
Flet が縮めていた (点火状態だけ約 72%)。煙つきの状態は、煙の場所を作る
ために機体そのものを右へ 14px ずらしていた。どちらも基点 (機体の中心) と
ずれる原因になる。

対策は、スロットを 35 の高さにして**機体は必ず同じ場所に置き、左側を
煙の置き場としてどの状態でも空けておく**こと。炎なしの機体も炎ありと
同じ viewBox の画像 (`_rocket_svg('')`) にして胴体の大きさをそろえた。
タイトル行が 11px 高くなるが、状態で行の高さが動かないほうが大事。

### 発射の経路

離陸で上がる高さ 105px と、弧の制御点「到達点の 60px 上」がどちらも
固定値だった。基点が画面の上寄りにあると、離陸だけで到達点の目前まで
来てしまい、続く弧で到達点より上まで行き過ぎてから下がってくる。
到達点までの距離に合わせて両方を頭打ちにした (`launch_path`)。
遠いカードの動きは従来と変わらない (テストで固定してある)。

### 却下確定の畳み込みも「演出 + 送信」の 2 フラグで

発射側 (`_try_auto_release`) は以前から「演出の終わり」と「送信の成功」の
両方がそろってから一覧を更新する 2 フラグ方式だったが、却下側は最初の
実装で送信後の再取得が抜けており、爆発が終わってもカードが畳まれずに
残る経路があった (レビューで検出)。却下側も同じ 2 フラグ方式にそろえ、
そろった時点でその場で畳む (`hide_pr` + `mark_auto_folded`。次の取得を
待たない)。送信が失敗したときは畳まず、取得し直して表示が戻る。

### 演出中に止めたカードの戻し方

演出中はロケットを透明にしてボタンを止める。戻すのは次の一覧描画だが、
**一覧の内容が前回と同じときは作り直さない**最適化があるため、そこを
通らず止まったままになる経路があった。止めるときに元の状態を覚えて
おき、描画のたびに戻すようにした (`_frozen_cards` / `_unfreeze_cards`)。
演出が全部終わるまでは戻さない (飛行中に常駐機が復活しないように)。

### 確かめ方

演出の見た目は目で見るしかないが、崩れると困るところはテストで固定した
(`manager/tests/test_manager_rocketfx.py`)。全状態で機体の大きさと位置が
同じこと、煙が機体に重ならないこと、発射が到達点を追い越して戻って
こないこと、遠いカードの経路が変わっていないこと。

## 承認の取り消しも楽観的更新に (2026-08, 「取り消しだけ反応が遅い」)

承認は押した瞬間に手元のデータを書き換えて描き直す (楽観的更新) のに、
**取り消しはボタンを凍結して送信 + 一覧の再取得を待ってから**表示が
変わる作りだった。体感でネットワーク 2 往復ぶん (数秒) 遅れ、
「承認 ⇄ 取り消し」の行き来で片方だけ重く感じる。

- 対策: 取り消しも承認と対称の楽観的更新にした。押した瞬間に自分の
  承認・却下を手元から除いて描き直し、送信は裏。失敗したら再取得で
  表示ごと戻る
- 却下確定の「却下を取り消す」も同じ経路なので、確定が解ける場合は
  畳みからの復帰 (unhide + 自動畳み記録の掃除) も押した瞬間に行う
- 手元に前回の取得結果がないとき (起動直後など) だけ、従来どおり
  ボタンを凍結して送信を待つ
- 確かめ方: 検証ハーネスで API に 2 秒の遅延を入れ、クリック 0.4 秒後の
  スクリーンショットで表示が反転していることを確認した

## 保存はまず「どこに置くか」をたずねる (2026-08, 管理者指示)

ダウンロードの印を押したとき、これまでは黙ってダウンロードフォルダへ
置いていた。**押したらまず保存先をたずねる**ようにそろえた。

- **理由**: 勝手にダウンロードフォルダへ入ると、あとで探せなくなる。
  提出の確認用データも過去の版の ZIP も「どこかの作業フォルダに置いて
  すぐ開く」使い方が多く、置き場所を選べるほうが手数が減る
- **対象**: 差分ダイアログの「確認用データを保存...」と、過去の更新ログの
  「ZIP を保存」。共通部品 `ask_save_path` (main.py) に集約し、
  差分ダイアログには関数として渡す (diffdialog は main.py に依存しない)
- **順番**: たずねる → (取り消しならここで終わり) → ボタンを止めて
  「作成しています...」→ 裏で作って書き出す。取り消したときは ZIP の
  組み立てすら始めない (数秒かかる処理を無駄に走らせない)
- **既定の置き場所**は従来どおりダウンロードフォルダ。ファイル名も従来と
  同じものを初期値に入れる (毎回打ち直さなくてよい)
- **保存ダイアログを出せない環境** (ブラウザ表示など) では、これまでどおり
  ダウンロードフォルダの空き名へ保存する。上書きは黙って行わない
- テスト: `manager/tests/test_manager_save_flow.py` で「先にたずねること」
  「選んだ場所に書くこと」「取り消したら何も作らないこと」を固定した

## 提出の説明文は空欄なら AI で自動記述 (2026-08, 管理者指示)

「更新内容」「制限事項」の案内を **「空欄の場合は AI で自動記述します。
(推奨)」** に変えた。あわせて提出時の確認ダイアログの既定を
「Claude で自動作成する (推奨)」に変更 (以前は「空欄のまま提出する」が
既定)。案内文と実際の既定がずれていると、案内が嘘になるため。

使用料のかかる処理なので、確認ダイアログで選び直せる形は残している
(黙って実行はしない)。「(扱いは提出時に選択)」の但し書きは、案内文が
そのまま既定を表すようになったため削除した。
