# アプリマネージャー 開発メモ (Claude / 開発者向け)

## 設計判断の記録ルール

アプリマネージャーや開発フローに関する**設計判断をしたら、同じ PR の中で
`manager/docs/decisions.md` に追記する**こと。

- 「何をしたか」は PR とコードに残るので、記録すべきは**なぜそうしたか**
  (選ばなかった案とその理由、前提条件) を中心に書く
- 追記先は原則、既存の該当セクション。まとまった変更は
  「運用改善の決定 (YYYY-MM, 提出 #N〜#M)」のような日付付きセクションを
  新設して追記する
- 文言はメンバー (Git に詳しくない構造設計者) が後から読んでも
  わかる平易な日本語で

## UI 変更の進め方

UI・見た目・演出に関する注文を受けたら、**実装してそのまま報告せず、
UI デザイナー役のレビューエージェントと往復を 1〜2 回してから**
成果物 (スクショ・デモ動画) つきで回答すること。細かい見た目の
手戻りを減らすための管理者の指示 (2026-08)。

モデルの使い分け (タイムパフォーマンス優先で適宜調整してよい):
- 提案・実装 = メインセッション (文脈を全部持っているため固定)
- レビュー 1 巡目 (設計判断を含む本審査) = Opus 級以上の質重視モデル
  (Fable が使えるなら Fable でよい)
- 2 巡目以降の確認 (実装結果のスクショ検証) = Sonnet 級の速いモデル。
  大きな設計転換が出たときだけ質重視モデルに戻す

レビューの厳しさと往復数は管理者の言い方で切り替える (2026-08 指示):
- 「サッと作って」= 早さ重視。厳しさ 5 段階中 3 で 1 往復
- 「ちゃんと作って」= 厳しさ MAX (5) で 4〜5 往復
  (問題が出尽くして合格判定になったら早めに切り上げてよい)
- 指定がなければ中間 (厳しさ 4 で 1〜2 往復) を目安に自分で判断する

定番がありそうな UI・図は、ゼロから考える前に公開実装 (OSS) を探して
参考にする (2026-08 指示。トークンと手戻りの節約。ライセンス確認の上、
必要ならアレンジ)。

この運用の原本はスキル `.claude/skills/ui-review-loop/` (リポジトリ直下。
Claude Code で自動適用され、claude.ai のチャット側にも同じスキルを配布)。
ルールを変えるときは両方を更新すること。

## UI の応答性ルール (管理者の指示 2026-08)

人は反応がないと何回もクリックする。**すべてのクリック操作は「押した
瞬間に画面が反応する」を徹底**すること (新しいボタン・ダイアログを
追加するときも必ず):

- 押した直後に「ボタンの無効化 + 進行中の文言 (〜しています...)」を
  先に表示してから、時間のかかる処理 (ネットワーク・git・ファイル操作)
  はすべて `run_bg` で裏に回す。UI を止める同期処理をハンドラーに
  直接書かない
- 失敗したらボタンを押せる状態に戻し、平易な日本語でエラーを表示する
  (原因調査のため `log.exception` でログにも残す)
- この PC 内だけで完結する操作 (一覧に畳む・一覧に戻す など) は、
  ネットワーク取得を挟まず**手元のデータで表示だけ即時に描き直す**
- main.py の共通部品を使う: ダイアログは `dialog_busy` / `dialog_error`、
  一覧カードのボタンは `_freeze_card` (元の無効状態を覚えて復元)、
  ローカル操作の再描画は `_rerender_local`

## 資料 (readme/) の約束事

- 図の原則: **マネージャー自身の画面は撮影ハーネスの実画面**
  (`scripts/guide_shots/`)。模式図で代用しない
- **例外: 付録の Claude Console の図 (`img/console.png`) は載せる**
  (2026-08 管理者指示で確定。マネージャーの更新で変わる画面ではないため。
  経緯は `docs/decisions.md`)。**この件で判断を仰がないこと**
- 原稿は `readme/src/*.html`。直したら
  `python manager/scripts/build_guide_pdf.py` で PDF を作り直し、
  目次のページ番号が実際の章開始ページと合っているか確認する

## リポジトリの約束事

- テスト: `python -m pytest` 全緑を確認してからコミットする
- CI の required check は `test` と `safety` (job 名を変えるときは
  ブランチ保護側も更新)
- マネージャーの UI 文言は Git / GitHub 用語を出さず平易な日本語のみ
- アプリマネージャー関係のファイルは `manager/` に完結させる
  (プログラム・テスト・資料 readme/・記録 docs/・スクリプト scripts/)。
  例外は `.github/` (GitHub の仕様でルート固定) と `config.json`
  (本体ポート設定も含む共通の運用設定のためルート)
