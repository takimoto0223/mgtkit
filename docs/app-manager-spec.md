# アプリマネージャー実装指示書

Claude Code への実装依頼書。以下の要件を読み、**Phase 順に**実装すること。
不明点・矛盾点があれば実装前に質問すること。

---

## 0. 背景と目的

- 対象: 複数の Python ファイルで構成された **Flask 製 Web アプリ**(既存リポジトリあり)
- 課題: 現在はバッチファイル直実行で環境構築〜起動まで行っており、バージョン管理・複数人での安全な機能追加の仕組みがない
- 目的: **Git / GitHub を一切意識させずに**、以下ができる「アプリマネージャー」(デスクトップアプリ)を作る
  1. 安定版の取得・更新・起動
  2. β版の試用
  3. 機能追加版の提出(裏側は Git ブランチ + PR)
  4. 3人承認による正式リリース

### 設計の大原則

- **状態は自前で持たない。** バージョン・差分・履歴・承認状態・レビューはすべて GitHub 側(ブランチ / PR / Releases / Reviews)を真実とし、マネージャーは「表示と操作の窓口」に徹する
- マネージャーが壊れても GitHub の画面から直接運用を継続できること
- ユーザーに Git 用語(branch / commit / merge / conflict)を見せない。通知・エラーは平易な日本語に翻訳する

## 1. リポジトリ構成・運用ルール

既存リポジトリに対して以下を整備する。

### 1.1 ブランチ

| ブランチ | 用途 | ルール |
|---|---|---|
| `main` | 安定版のみ | 直 push 禁止。PR 必須。**3人の Approve 必須**(ブランチ保護で強制) |
| `feature/*` | 提出ごとに自動生成 | マネージャーが作成。命名: `feature/{ユーザー名}-{YYYYMMDD}-{連番}` |

### 1.2 ブランチ保護(管理者が一度だけ実行するスクリプトとして生成)

- `main`: 直 push 禁止 / required approving reviews = 3 / ステータスチェック(CI)必須
- `gh api` を用いたセットアップスクリプト `scripts/setup_repo_protection.sh`(または .bat)を作ること

### 1.3 バージョニングと Releases

- 安定版: `vX.Y`(例 `v1.2`)として GitHub Releases に登録
- β版: `vX.Y-beta.N`(例 `v1.3-beta.1`)として **プレリリースフラグ付き** で登録
- CI がβ版タグ付けを自動で行う(後述)

### 1.4 version.json(重要)

配布物(安定版・β版とも)のルートに、リリース作成時に自動生成して同梱する:

```json
{
  "version": "v1.2",
  "commit": "<コミットSHA>",
  "distributed_at": "YYYY-MM-DD"
}
```

- これが「提出者がどの版を基に改造したか」を特定する唯一のキーとなる
- リリース用 ZIP を作る CI ステップで自動書き込みすること

### 1.5 .gitignore / リポジトリ衛生

- `__pycache__/`, `venv/`, `.env`, `*.db`, ローカル設定, IDE ファイル等を整備
- 依存は `requirements.txt` で固定(バージョンピン留め)

## 2. アプリマネージャー(自作するデスクトップアプリ)

### 2.1 技術選定

- **Python + Flet** を第一候補とする(Flask アプリと言語を揃える。UI を Web アプリと近い見た目にしやすいため。Tkinter は不採用)
- 対象 OS: Windows
- GitHub 操作は `gh` CLI(認証済み前提)と `git` コマンドをサブプロセスで叩く。トークンをマネージャー内に保存しない
- Anthropic API キーは環境変数から読む(コードに埋め込まない)

### 2.2 画面構成(4タブ + 承認タブ)

#### タブ1: 起動

- 手元の安定版のバージョン表示(version.json を読む)
- 「起動」ボタン → 安定版 Flask アプリを起動しブラウザを開く(Git 操作なし)

#### タブ2: 更新

- GitHub Releases の最新安定版と手元バージョンを比較
- 新しい版があれば「更新があります」表示 + リリースノート(更新内容)表示
- 「更新して起動」ボタン → 最新安定版を取得・依存インストール・起動
- 依存(requirements.txt)の更新もここで面倒を見る

#### タブ3: β版

- プレリリース一覧を `gh release list` から取得して表示
- **誰でも試用可**(オープン方針)
- 「試す」ボタン → **安定版とは別フォルダに展開し、別データ(DB・設定を分離)、別ポートで起動**
  - 例: 安定版 `%USERPROFILE%\AppData\Local\<app>\stable\`(port 5000)/ β版 `...\beta\<version>\`(port 5001〜)
- β版画面には「これはβ版です」の明示バナー(Flask 側に環境変数で伝える等)
- フィードバック入力欄 → 対応する PR にコメントとして投稿(`gh pr comment`)。承認判断の材料にする

#### タブ4: 提出(機能追加版のアップロード)

ユーザー操作は「ZIP を選んでアップロード」だけ。裏側フロー:

```
1. ZIP を受け取り展開
2. 同梱の version.json から基点コミット SHA を読む
   - version.json が無い/壊れている → エラー表示して中断
3. 安全チェック(2.3)を実行。NG なら理由を表示して中断
4. 基点コミットから feature ブランチを作成
5. 作業ツリーに ZIP の中身を上書き
6. 「基点にあったが ZIP に無いファイル」を列挙し、
   「削除されたファイル: xxx.py — 意図的な削除ですか?」の確認ダイアログ
   - 意図的 → 削除として commit に含める
   - 入れ忘れ → 基点のファイルを維持
7. コミットメッセージ: ユーザー入力欄(空なら Claude API で diff から生成)
8. commit → push → gh pr create
   - PR 本文: Claude API で「更新点のまとめ」を自動生成
   - PR タイトル: バージョン候補 + 機能概要
9. 完了画面: 「提出しました。検証と承認が済むと配布されます」+ PR URL
```

**衝突時(基点より main が先行し、同一箇所が変更されていた場合):**

```
1. マネージャーが merge を試行し、衝突を検出
2. 衝突箇所とその前後のコードを Claude API に渡し、
   「機能レベルの説明」に翻訳させる
   例: 「main.py で、あなたの機能a(CSV出力)と、
        最新版の機能b(ログ強化)が同じ関数を変更しています」
3. 選択画面を表示:
   ◉ 両方の機能を残す(推奨・デフォルト)
   ○ 自分の機能を優先(相手側の該当部分を破棄)
   ○ 最新版を優先(自分の該当部分を破棄)
4. 選択結果を Claude への指示として渡し、コードレベルの統合を実行
   → 統合結果を commit して PR を更新
```

チェックボックス/ラジオボタンは **Git を直接操作するものではなく、Claude への指示書**である。

#### タブ5: 承認(全メンバーに表示)

- 承認待ちβ版の一覧(= open な PR + β リリース)
- 各項目に **黄色マーカーで「承認 n/3」** のステータス表示(`gh pr view --json reviews` から Approve 数を集計)
- 承認済みメンバーの表示
- 「承認」ボタン → `gh pr review --approve`
- 「却下」ボタン → コメント必須 → `gh pr review --request-changes`
  - 1人でも却下があれば承認数に関わらずブロック表示
  - 却下理由は提出者へ平易な日本語で通知表示
  - 差し戻し後の修正は「修正版 ZIP を再提出 → 同一 PR に積む」フローで対応
- **提出者本人は自分の提出を承認できない**(マネージャー側で制御)
- 差分表示: **提出者の変更と Claude の自動修正を色分け**して表示
  - Claude 修正 commit には識別可能なプレフィックス(例 `[auto-fix]`)を付け、それで判別
- 3人承認が揃うと「リリース」ボタンが有効化(管理者のみ) → squash merge → 正式版タグ → Releases 登録
- マージ完了後、全員のマネージャーが次回起動時/ポーリングで「新しい安定版があります」を通知

### 2.3 提出時の安全チェック

1. **拡張子ホワイトリスト**: `.py .md .txt .json .html .css .js .yml .yaml .cfg .ini .csv` 等、プロジェクトで想定されるもののみ。`.exe .dll .bat .ps1 .sh` 等の実行ファイルは即ブロック
2. **サイズ・ファイル数上限**: ZIP 展開後合計サイズとファイル数に上限(設定ファイルで変更可)
3. **秘密情報スキャン**: `detect-secrets` または `gitleaks` を実行し、API キー・パスワード様文字列があれば警告(ユーザー確認の上で続行可否)
4. **依存監査**: `requirements.txt` に差分があれば `pip-audit` を実行。新規パッケージ追加は承認画面に赤字で明示
5. マルウェアの完全検出は不可能である前提に立ち、**最終防衛線は 3 人承認プロセス**とする。承認画面に Claude による「危険な操作(ファイル削除・外部通信・サブプロセス起動・eval 等)の有無」の要約を表示する

## 3. 自動パイプライン(GitHub Actions)

### 3.1 PR 作成時のワークフロー

```
PR opened / synchronize
  ↓
[ジョブ1] テスト
  - 依存インストール(requirements.txt)
  - Level 1 スモークテスト: アプリが例外なく起動し、主要 URL が 200 を返す
  - Level 2 回帰テスト: pytest 一式
  ↓
[ジョブ2] 安全チェック
  - gitleaks(secrets スキャン)
  - requirements.txt 差分があれば pip-audit
  - tests/ 配下に diff があれば fail(後述ガード)
  ↓
全部パス → β版タグ付け(vX.Y-beta.N)+ プレリリース作成
           + 配布 ZIP に version.json を書き込んで添付
失敗     → Claude 自動修正ループ(3.2)
```

### 3.2 Claude 自動修正ループ

- `anthropics/claude-code-action` を使用(ANTHROPIC_API_KEY は repo secrets に設定済み前提)
- フロー:

```
テスト失敗
  ↓
失敗ログを Claude に渡し、原因分析 + 修正 commit を PR に積む
  ↓ テスト再実行
  パス → β版へ。ただし PR に「AI修正あり」ラベル付与
  失敗 → 再修正(最大3回)
  ↓ 3回失敗
  ループ強制終了
  - PR に「自動修正失敗」ラベル
  - Claude に「Git を知らない人向けに、何が起きたか・
    どうすればよいかを3行で」平易な要約を書かせ、PR コメントに投稿
  - マネージャーの提出タブに「検証を通過できませんでした」+ 要約を表示
  - 管理者判断待ち
```

- **修正ループのガード(必須・4点)**:
  1. **tests/ 配下の変更・削除は禁止**。プロンプトで明示 + Actions 側でも「AI 修正 commit に tests/ の diff があれば fail」の二重チェック
  2. 修正 commit は `[auto-fix]` プレフィックス必須(承認画面の色分け判別用)
  3. 修正 commit メッセージに「なぜ失敗していたか・何を変えたか」の説明を必須とする
  4. 禁止パターンをプロンプトに明示: bare except による例外の握りつぶし / テストの skip 追加 / アサーションの緩和 / 仕様の変更

### 3.3 マージ後のワークフロー

```
main へマージ
  ↓
正式版タグ(vX.Y)+ Releases 登録
  + リリースノート(Claude で PR 群から生成)
  + 配布 ZIP に version.json 書き込み
```

## 4. テスト整備(初期作業として実施)

現状テストは存在しない。以下の順で Claude Code が整備する:

1. **Level 1(スモークテスト)**: Flask アプリが起動し、主要ルートが HTTP 200 を返すことの確認。`pytest` + Flask の test_client を使用
2. **Level 2(回帰テスト)**: 中核ロジックの入出力テスト。主要機能を洗い出してから作成
3. **Level 3(運用ルール)**: 提出パイプラインに「差分に対するテストを Claude が自動生成して PR に同梱する」ステップを組み込む(3.1 のワークフローに追加)。これによりテストは提出のたびに育つ

## 5. セットアップ用スクリプト

メンバー配布用に以下を生成すること(既存のバッチ設計を流用可):

- `setup.bat`: winget で Git / gh / (必要なら Python) を導入 → `gh auth login`(対話・Web 認証)→ マネージャーの取得と起動まで
- `scripts/setup_repo_protection.sh|bat`: 管理者用。default branch 設定・ブランチ保護(3 approvals)・repo secrets の案内

## 6. 実装フェーズ分割

以下の順で実装し、各 Phase 完了ごとに動作確認を挟むこと:

- **Phase 1**: リポジトリ整備(.gitignore / requirements 固定 / ブランチ保護スクリプト)+ テスト Level 1-2 の作成 + CI(テスト実行のみ)
- **Phase 2**: マネージャーの起動・更新・β版タブ(読み取り系。GitHub Releases 連携)
- **Phase 3**: 提出タブ(ZIP → ブランチ → PR の自動化、削除ファイル確認、安全チェック)
- **Phase 4**: Actions の Claude 自動修正ループ + β版自動リリース
- **Phase 5**: 承認タブ(n/3 表示、承認/却下、色分け差分、リリース)+ 衝突解決フロー
- **Phase 6**: 通知まわり・仕上げ(更新通知、フィードバック→PR コメント連携)

### 各 Phase 共通の注意

- Windows 環境で動作すること(パス区切り・エンコーディング cp932/UTF-8 混在に注意)
- サブプロセスで git / gh を呼ぶ際は失敗時の stderr をログに残し、ユーザーには平易な日本語メッセージを表示
- 設定値(リポジトリ名、ベースブランチ、ポート番号、承認必要数=3、ループ上限=3、サイズ上限等)は `config.json` に外出しし、ハードコードしない
